# LLM 自动化 Web 渗透测试 —— 有效性评估与架构建议

> 日期：2026-10-26　|　范围：vuln-range 项目（ARTEX + 本地网关 + 靶场 8899）
> 结论先行：**"能做"和"有效"是两个问题。做得到，但当前证据不足以宣称有效。**
> 本文所有数字均来自本机实测，未实测处明确标注 `?`。

## 一、"由我作为模型层"的三条实现路径

| 路径 | 可行性 | 判断依据 |
|---|---|---|
| **A. ARTEX 调用 WorkBuddy 的 LLM 当后端** | ❌ **不可行** | ① 我本身不暴露 OpenAI 兼容端点；② WorkBuddy cloud-service LLM 只支持流式、靠 Origin 精确鉴权、文档明令禁止"自建 BFF/代理转发"与手拼 `/.cloud/llm/*`；③ 渗透工具是独立进程，必须走 HTTP 回调模型 |
| **B. 我直接作为 agent 驱动整条链**（shell + 脚本 + 分析 + 迭代） | ✅ **现在就能跑** | 我具备：执行命令、写脚本、读响应、循环验证、落库报告。不依赖任何外部 API key，也不受 Docker 阻塞 |
| **C. 混合：我出策略与复核，机械劳动交给工具** | ⚠️ **部分可行** | ARTEX 可用（但模型走 NVIDIA 网关）；strix/shannon/pentagi 需 Docker → 当前卡在 hypervisor 未加载 |

**关键澄清**：用户设想的大概是 A，但真正可行且更强的是 **B/C** —— 因为 LLM 在渗透中的价值不在"循环跑工具"，而在"看一眼响应就知道下一步该试什么"。

## 三、"有效"必须用四个硬指标定义（否则无法证伪）

1. **精确率 precision** = 真漏洞 / 报告总数　→ 衡量误报（当前 #42 是反例）
2. **召回率 recall** = 发现数 / 埋设的 ground truth 总数 → 衡量漏报（当前任务 11 是反例）
3. **可复现性** = 每条 finding 能否被**独立脚本**重放成功（不依赖 LLM 上下文）
4. **稳定性** = 同一目标重跑 3 次，finding 集合的 Jaccard 相似度

> 行业里被默认忽略的是 2 和 3。大多数"AI 渗透工具"的 demo 只在演示 1，且没有 ground truth。

## 四、LLM agent 的能力边界矩阵（决定能打什么）

| 漏洞类别 | 适用度 | 原因 |
|---|---|---|
| SQLi / 命令注入 / SSTI | 🟡 中高 | 需闭合、注释、编码绕过的推理；LLM 强，但穷举不如 sqlmap |
| 反射/存储型 XSS | 🟡 中 | payload 变体构造是强项；上下文判定易误报 |
| 信息泄露 / 配置错误 / 敏感头 | 🟢 高 | 读响应、读 JS、读报错就能定位 |
| API 端点发现（SPA / JS bundle） | 🟢 高 | 扫描器看不见 JS 里的路由，LLM 能读 |
| 认证 / 会话 / JWT 缺陷 | 🟡 中 | 需要理解"谁该看到什么" |
| **越权 / IDOR / 业务逻辑** | 🔴 低 | 需要业务语义 + 多账号 + 状态机，LLM 易过度自信 |
| CSRF / 点击劫持 / 缺失安全头 | 🔴 低 | 纯机械检查，扫描器更全更快 |
| 文件上传 → RCE 链 / SSRF → 内网 | 🟡 中 | 强在串联，弱在稳定复现 |

**一句话**：LLM 是"分析员"，不是"扫描器"。用 LLM 替代扫描器必然漏报；用 LLM 替代分析员才是正解。

## 五、LLM agent 真正强过扫描器的四个场景

1. **白盒（有源码）**：读 sink（`cursor.execute(f"...{q}")`）→ 反推精确 payload，扫描器只能盲猜
2. **SPA / API 型目标**：从 JS bundle 提路由与参数名，扫描器爬不到
3. **告警收敛**：nuclei 出 800 条 → 我判断哪 3 条是真的
4. **多步串联**：SSRF → 内网探活 → 越权读配置 → 提权，需要跨步骤记忆

反过来，**该交给机械工具、不要交给 LLM** 的：目录爆破、CVE 特征匹配、参数 fuzzing、端口扫描。

## 六、推荐架构（把"我"放在正确的位置）

```
┌─ 我（编排 + 推理 + 验证）
│   ├─ 侦察层：爬虫 / JS 解析 / 端点枚举        → 脚本（确定性）
│   ├─ 扫描层：nuclei / sqlmap / nikto          → 机械穷举（广度）
│   ├─ 推理层：漏洞假设 / payload 变体 / 链式利用 → 我（深度）
│   └─ 验证层：每条 finding 用独立脚本重放       → 我 + 脚本（把关）
└─ 产出：report.md（含逐条 curl、影响、修复）
```

**为什么 ARTEX 会 #43 真执行转账**：它的循环是
`LLM 决策 → 执行 → report_finding`，中间**没有人在环、没有独立验证**。
它的 `intercept` 包（allow/deny/ask + guard）默认未启用 → 破坏性动作直接落地。
→ 把"验证层"补上，就是这套东西从"危险玩具"变成"可用工具"的唯一分界。

## 七、红线（不变，写死）

1. 只打**自有资产 / 自建靶场 / 本地代码审计**
2. 不把 ARTEX 用于任何外部赏金 program（工具指纹 + 该工具已有武器化前科，无法自证授权）
3. 任何"写操作 / 改数据 / 转账"类动作 → 默认 deny，需人工确认

## 八、下一步：唯一能给"有效"下结论的实验

**A/B 对照实验（可立即执行，1-2 小时）**

- **Ground truth**：在靶场 8899 埋 5 个已知漏洞（SQLi / 反射 XSS / IDOR / 命令注入 / 路径穿越），
  每个都有明确的"漏洞点 + 正确利用方式"，不给工具任何提示
- **A 组**：ARTEX（超时 30 分钟，ultra-550b，单 worker）
- **B 组**：我直接驱动（侦察 → 假设 → 验证，逐条独立复现）
- **C 组（基线）**：nuclei + sqlmap 常规跑
- **指标**：precision / recall / 可复现性 / 耗时 / token 消耗

输出对照表后，"能不能有效"才有答案。**在此之前，任何结论都只能是假设。**
