# patched 反事实差分 · 验收报告

> 日期：2026-11-02
> 目标：把闸门的 `confirmed` 从 **signal 级** 抬到学术口径（arXiv 2608.09567 的
> `available → runnable → signal → confirmed` 四级阶梯）
> 验收命令：`python diffcheck.py --repeats 3 --label diff-v2`
> 结果：**11 / 11 通过**（同一 GT、同一 payload、只换被测实现）

---

## 1. 为什么必须做这一步

在此之前，闸门的对照是**benign 请求**。它能排除：

- 页面本来就回显这个字符串
- 响应形状是通用行为（错误页、SPA 外壳）

它排除不了：

- **这个版本本来就这样**（漏洞根本不存在，是判据写错了）

领域里最相关的一篇（arXiv 2608.09567《From Runnable to Verifiable》）明确论证：
在 vulnerable build 上看到触发信号，不等于漏洞被复现，**必须有干净的 patched 反事实**。
它举的例子是 CVE-2020-1967 的 PoC 调 `SSL_check_chain(NULL)` —— 任何版本都会崩。

所以此前所有 `confirmed`，严格讲都只是 `signal`。

---

## 2. 方法：同一份 GT，只换被测实现

给 lab 加了 `LAB_MODE` 开关（`lab/lab_app.py`）：

| 模式 | 启动方式 | 含义 |
|---|---|---|
| `vuln`（默认） | `python lab/lab_app.py` | 故意留洞，**历史行为一字未改** |
| `secure` | `LAB_MODE=secure LAB_PORT=8895 python lab/lab_app.py` | 每条漏洞按标准修复模式改掉 |

两条硬约束，保证"差异只来自修复点"：

1. **GT 完全不动**：`request / assert / control / control_assert` 一个字段都不改。
   跑 secure 版用的还是 `lab/ground_truth.json` 原文件。
2. **profile 的 artifacts 完全一致**：`profiles/lab_secure.json` 是从 `lab.json` 复制的，
   只有 `base`（8895）与 `control_token_file` 不同。判据用到的真值（canary、密钥、UID）
   完全相同 —— 否则差分会混入"判据变化"。

`diffcheck.py` 做的事：起两个实例 → 各跑一遍同一份 GT → 逐条对照 → 输出强度分级。

### 判据（硬，不接受"差不多"）

| secure 版结果 | 是否通过 | 强度 | 含义 |
|---|---|---|---|
| `rejected` | ✅ | 强 | 判据所依赖的可观测事实在修复后消失 |
| `blocked` | ✅ | 中 | 被鉴权层挡下，需交叉验证（见 §3.2） |
| `confirmed` | ❌ | — | 这个"修复"没有改变任何可观测事实 |
| `unknown` | ❌ | — | 判不了，**不等于修好了** |
| vuln 版不是 confirmed | ❌ | — | 基线失效，差分无从谈起 |

## 3. 结果

### 3.1 总表（11/11 通过）

| CASE | 有洞版 | 主请求 | 修复版 | 响应码 | 强度 | 闸门给出的断言说明 |
|---|---|---|---|---|---|---|
| SQLI-01 | confirmed | 200 | rejected | 200 | 强 | `contains=False` |
| XSS-01 | confirmed | 200 | rejected | 200 | 强 | `raw=False escaped=True forms=1` |
| IDOR-01 | confirmed | 200 | rejected | 403 | 强 | 响应里已无 `user_id` 字段 |
| CMDI-01 | confirmed | 200 | rejected | 400 | 强 | `json[output] contains CMDI-MARKER = False` |
| LFI-01 | confirmed | 200 | rejected | 403 | 强 | `contains=False` |
| SSRF-01 | confirmed | 200 | rejected | 403 | 强 | `contains=False` |
| PRIV-01 | confirmed | 200 | rejected | 403 | 强 | post 步骤 403 |
| DEFAULTCRED-01 | confirmed | 200 | rejected | 401 | 强 | post 步骤 403 |
| DBWRITE-01 | confirmed | 200 | rejected | 403 | 强 | post 断言 not-contains |
| HIDDEN-01 | confirmed | 200 | blocked | 401 | 中 | 需交叉验证 |
| EXPOSE-USERS-01 | confirmed | 200 | blocked | 401 | 中 | 需交叉验证 |

**最关键的两条是 SQLI-01 和 XSS-01**：修复版**返回 200，页面完全正常**，只是数据没被拖出来、
标签被转义了。这是最强形态的证据 —— 不是"应用坏了所以打不通"，而是"应用好好地活着，洞没了"。

### 3.2 中等强度两条的交叉验证

`blocked` 只说明"被挡住了"，它无法区分：

- (a) 修复加了鉴权 → 挡住
- (b) 这个端点本来就要登录 → 挡住

于是用**普通用户 bob 的真实会话**再打一次：

```
普通用户 bob 登录：200，拿到会话：True
/api/users               -> 200  ✅ 数据不可见
/api/internal/export     -> 401  ⚠ 被拦（401），无法区分是鉴权还是本来就要求登录
```

- **EXPOSE-USERS-01 升级为强证据**：返回 200，但响应里**没有 `api_key` 字段、没有 `AK-LIVE`**。
  修复不是靠 401 挡人，而是真的裁掉了敏感字段。
- **HIDDEN-01 仍是中等**：原因见 §4.3，是修复之间的连锁效应，不是闸门的问题。

### 3.3 "修复没把应用修坏"的证据

如果 secure 版把所有请求都打成 403，差分就是假的。所以额外验证**正常路径**：

| 检查项 | 结果 |
|---|---|
| secure 版 control 断言全部成立 | **11 / 11** |
| 普通用户 bob 能正常登录 | 200 |
| bob 能正常访问 `/api/users` | 200 |

也就是说：修复精准作用于攻击路径，benign 路径行为不变。

## 4. 过程中新发现的三个问题

### 4.1 🔴 一整类漏洞无法验证：3xx 型（最严重）

做差分时想加一条"开放重定向"探针，结果实测发现闸门**根本看不到 Location 头**。

`do_request` 用的是 urllib 默认 opener，**自动跟随重定向**。实测：

```
请求 GET /go?to=/admin
  status    : 200
  final_url : http://127.0.0.1:8896/login?next=/admin
  redirected: True
  Location  : None            ← 证据彻底消失

assert status==302        -> (False, 'status=200 expect 302')
assert Location 含 /admin -> (False, 'contains=False')
```

后果不是"判错"，而是**静默漏报**：

| 漏洞类型 | 修复前表现 |
|---|---|
| 开放重定向 | 跟随到目标页 → 证据丢失 → `rejected`（读作"漏洞不存在"） |
| CRLF 注入到 Location | 头被重定向处理吃掉 → 同样漏 |
| 重定向型 SSRF | 跟随链让"服务端去了哪"变得不可辨 |
| OAuth 回调白名单缺失 | 同上 |

**修法**（已实现并验收）：

1. `verify.py` 新增 `_NoRedirectHandler`；step 支持 `"no_redirect": true`
2. 新增三种断言：`header_contains` / `header_not_contains` / `header_equals`
3. 夹具 `lab/legacy_app.py` 新增 `/go?to=` 端点（无白名单）
4. GT 新增两条互为对照的 case：

| CASE | 期望 | 实测 |
|---|---|---|
| LEGACY-OPENREDIR（`to=https://evil.example.com/`） | confirmed | ✅ `header location='https://evil.example.com/'` |
| LEGACY-OPENREDIR-BLIND（`to=/public`） | rejected | ✅ 同端点安全参数不出现攻击者域名 |

夹具全套 **4/4 符合预期**（blocked 1 / confirmed 2 / rejected 1）。

A/B 对照（同一条开放重定向）：

```
带 no_redirect（修复后）  -> confirmed
不带 no_redirect（修复前）-> unknown（transport error）
```

> 注：修复前如果重定向目标是站内可达路径，会跟随完再判 `rejected` —— 这比 `unknown` 更危险，
> 因为它看起来像一个确定的否定结论。

### 4.2 `observations[i].status` 是"最终响应"，不是"主请求响应"

`diffcheck` 第一版把 `DEFAULTCRED-01` 修复版显示成 403，而实际主请求是 401。
原因是 bundle 里的 `status` 记录的是**该轮最后一个步骤**（post）的响应。

这不是 verify 的 bug（它记录了完整 `steps`），但**任何只看 `status` 的消费方都会误读**。
已在 `diffcheck.py` 里改为按 `phase=attack` 从 `steps` 取，并同步在报告表里加"主请求"列。

**教训**：多步 case 的顶层 status 有歧义，消费方必须显式说明自己取的是哪一步。

### 4.3 修复之间存在连锁效应

`HIDDEN-01` 无法升级为强证据，原因是一条因果链：

```
DEFAULTCRED-01 的修复：禁止 admin 用默认口令登录
        ↓
secure 版无法用 admin 登录
        ↓
/api/internal/export 要求 admin
        ↓
无法用管理员会话验证"返回内容里到底有没有密钥"
```

这不是设计失误 —— **真实补丁之间本来就会互相影响**。但它说明：
差分实验要规划修复顺序，否则后置验证会被前置修复挡住。

## 5. 自我批评：构造效度

这是本次最容易自我欺骗的地方，必须写清楚。

**我们既是出题人，也是修复人。**

修 `XSS-01` 的时候，我知道断言是 `body_contains "<svg/onload=alert(1)>"`，所以只要 `html.escape`
就能让它过。修 `SQLI-01` 时，我知道断言看的是 `AK-LIVE`，所以只要不返回 `api_key` 就能过。
严格讲，这仍然**不等于**"独立的 patched build 反事实"。

已做的缓解：

| 措施 | 可验证结果 |
|---|---|
| 修复按**标准模式**写，不是照着断言打补丁（参数绑定 / 输出编码 / 对象级授权 / 命令白名单 / 协议+地址白名单 / 功能级授权 / 服务端重算金额） | 代码里每条修复都注明了是哪一种标准做法 |
| 修复后**正常路径必须仍然工作** | control 11/11 成立、bob 登录正常、`/api/users` 200 |
| 判据不参与修复设计 | GT 是 10-28 就写好的，修复是 11-02 才写 |

但这条路的天花板是明确的：**只有当修复者不知道判据时，差分的证明力才是满的。**
现实中可操作的替代是：让我先写修复，再由一个不知道判据的流程跑 GT。这在本机环境下
做不到（只有一个操作者），所以本报告把结论限定为：

> 11/11 证明的是「这些漏洞的存在依赖于具体实现缺陷，而不是判据自身的问题」。
> 它比 benign 对照强一档，但**不是**完全独立的第三方复现。

## 6. 顺带做的两件卫生工作

### 6.1 证据目录分代（239 条历史 bundle 归档）

归档前 `evidence/` 有 **314 条** bundle，其中 **239 条（76%）没有 `mode` 字段**，
无法区分「正式攻击」「负样本自检」「弱化实验」。其中 16 个 case 只有 legacy bundle。

已移到 `evidence/_legacy/`（**只移动、未删除、内容未改**），并生成 `INDEX.md`
逐条记录 case / verdict / reason / 文件名。

验收：

| 检查 | 结果 |
|---|---|
| `evidence/*.json` | 75 条（全部带 mode） |
| `evidence/_legacy/*.json` | 239 条 |
| lab 11 条最新结论 | **11/11 confirmed 不变** |
| `tally.py` 汇总 | 正常，Juice Shop oracle 不受影响 |

### 6.2 凭据隔离

`profiles/juiceshop.json` 里原本带着 2 个真实 JWT（payload 内含密码哈希）和明文密码。
已抽出到 `profiles/juiceshop.secrets.json`，主文件只留 `<REDACTED>` 占位。
`asserts.load_profile()` 支持同名 `.secrets.json` 覆盖 artifacts（缺失时行为与旧版一致）。

配套 `.gitignore` 覆盖：`.token`、`.nvidia_key`、`profiles/*.secrets.json`、`evidence/` 等。

验收：Juice Shop 两条抽样回归 `J-IDOR-BASKET` / `J-USERLIST` 仍 confirmed。

## 8. 仍未解决的（如实列出）

1. **构造效度**（§5）：出题人与修复人是同一个，证明力有上限。
2. **HIDDEN-01 只有中等强度**：被 DEFAULTCRED 的修复连锁挡住（§4.3）。
3. **secure 版共用同一份 sandbox 目录**：两实例同时跑时 `canary.txt` 是共享的。
   目前都是只读，不影响结论；但若将来加"文件写"类修复，必须隔离目录。
4. **差分只覆盖 lab 的 11 条**：Juice Shop 是第三方预编译包，没有 patched 版本可用，
   所以真实应用上的结论**仍然只有 signal 级**。
5. **单模型不可复现**：LLM 层仍在本会话里。

## 9. 一句话

> 以前能说「这个洞在我这儿被打出来了」；
> 现在能说「把这个洞按标准方式修掉之后，同一发 payload 就打不出来了，
> 而且应用的其他功能照常工作」。
>
> 前者是现象，后者才是证据。
