## 一、这轮真正解决的问题：Locate 从「人工 grep」变成「AST 反向可达」

第一轮的定位方式是一句 `grep -n "= castPath("` 加人眼判读。它有两处硬伤，
都是这轮用工具跑出来才发现的：

| 硬伤 | 后果 | 这轮的修法 |
|---|---|---|
| 只找到**直接**调用 sink 的函数 | `var invoke = baseRest(baseInvoke)` 这种包装层 grep 不到。第一轮能发现 `_.invoke` 纯靠手工记忆，不是工具发现的 | 补「包装器别名」节点：`baseRest/baseAry/overRest/flatRest` 把参数函数记成调用边 |
| guard 靠人眼找 | 换版本要重来一遍，不可复现、不可 diff | 内置 6 种 guard 形态探测，输出可 diff 的 JSON 矩阵 |

**这一条要写清楚，因为它决定了后续所有结论的可信度**：第一轮报出来的
`_.invoke` 是「先想到再验证」，不是「工具扫出来的」。工具建好之后重跑，
`_.invoke` 是被自动列进「无防护」名单的 —— 两件事的价值完全不同。

### 工具设计上被实测打出来的三个错

1. **sink 集一开始混了 `assignValue`** → `clone` / `keys` / `max` 等 44 个纯数据
   操作全被报成「攻击面」。`assignValue` 不是 path sink，它是通用属性写入，
   `baseClone` 复制对象时也走它。收紧到 `baseSet / baseUnset / baseAssignValue`。
2. **`var method = baseRest(function(){})` 的函数表达式父节点是 CallExpression**，
   不是 VariableDeclarator。只看 parent 会得到匿名函数，`_.method` 整个消失。
   改成同时看 parent + grandparent。
3. **guard 判定一开始按「出现 `__proto__` 就算有」** → `baseUnset` 在 4.17.23 的
   partial 修复（只挡 `__proto__`、不挡 `constructor.prototype`）会被判成 full，
   而 4.17.23 的绕过恰好走的就是 `constructor.prototype`。现在按 sink 语义分档。

## 二、结构性证据：同一不变量，三个 sink，三种待遇

用同一套 AST 分析跑三个版本，得到可直接 diff 的表：

| API | 4.17.20 | 4.18.0 | 4.18.1 |
|---|---|---|---|
| `invoke` | baseInvoke / **none** | baseInvoke / **none** | baseInvoke / **none** |
| `invokeMap` | baseInvoke / **none** | baseInvoke / **none** | baseInvoke / **none** |
| `method` | baseInvoke / **none** | baseInvoke / **none** | baseInvoke / **none** |
| `methodOf` | baseInvoke / **none** | baseInvoke / **none** | baseInvoke / **none** |
| `result` | result / **none** | result / **none** | result / **none** |
| `set` | baseSet / full | baseSet / full | baseSet / full |
| `unset` | baseUnset / **none** | baseUnset / **full** | baseUnset / full |
| `update` | baseSet / full | baseSet / full | baseSet / full |

`baseUnset` 的 `none → full` 恰好发生在 4.18.0，与 GHSA-f23m-r3pf-42rh 的
patch 完全吻合 —— 这同时说明**工具没有瞎报**（校准通过）。

`baseInvoke` 三个版本全 `none`：**它不是回归，是从未被覆盖**。

guard 证据（4.18.1 实采）：

```
baseSet     @4025 -> {protoKey:true, ctorKey:true, protoWord:true, returnsOnBlock:true}
baseUnset   @4376 -> {protoKey:true, ctorKey:true, protoWord:true, ownCheck:true}
baseInvoke  @3260 -> {protoKey:false, ctorKey:false, protoWord:false, ownCheck:false}
```

## 三、影响面：7 个入口，全部 RCE

矩阵装置 `matrix.py` 跑出（17 载荷 × 3 版本，一载荷一进程）：

| 载荷 | 4.17.20 | 4.18.0 | 4.18.1 |
|---|---|---|---|
| `invoke_rce_arr` | HIT | HIT | HIT |
| `invoke_rce_str` | HIT | HIT | HIT |
| `invokeMap_rce` | HIT | HIT | HIT |
| `method_rce` | HIT | HIT | HIT |
| `methodOf_rce` | HIT | HIT | HIT |
| `lazy_invokeMap_rce` | HIT | HIT | HIT |
| `chain_invokeMap_rce` | HIT | HIT | HIT |
| 5 条 pollution 载荷 | HIT | HIT | HIT |
| `unset_same_path_blocked`（canary） | — | OK | OK |
| `set_same_path_blocked` | OK | OK | OK |
| 3 条正常功能对照 | OK | OK | OK |

两个必须注意的点：

1. **`unset` 那行是 canary，不是失败**。它显示 4.17.20 没拦住、4.18.x 拦住了 ——
   这证明装置有区分「修了 / 没修」的能力。没有这一行，上面所有 HIT 都不能信。
2. **正常功能对照全 OK**：说明缺 guard 的不是「为了功能才这么写」，
   `set` 加了三道 guard 之后 `_.set/_.get` 正常工作，`_.invoke` 正常路径也正常。

### 字符串路径同样成立，这比数组路径重要

```js
_.invoke({}, '__proto__.constructor.constructor', 'return process.version')()  // v22.22.2
```
很多应用把用户输入直接当 path 传给 `_.invoke`（`_.invoke(obj, userKey)`）。
数组形态要求攻击者能控制数组，字符串形态只要控制一个字符串 —— 利用门槛低一个档。

### 分发形态：三种中了三种

| 形态 | 结果 |
|---|---|
| `require('lodash')` 全量 UMD | `v22.22.2` |
| `require('lodash/invoke')` 单体模块（按需引入） | `v22.22.2` |
| `import { invoke } from 'lodash-es'`（ESM） | `v22.22.2` |
| `lodash/fp` 的 `fp.invoke` | **未打通**（见下） |

单体模块中招很重要：很多项目为了减小包体积只 `require('lodash/invoke')`，
这不构成任何缓解。

## 四、诚实边界（这轮新增的三条）

1. **`lodash/fp` 未复现，不等于安全。** `fp.invoke` 经过 `convert()` 重排了
   参数顺序并做了柯里化，我试了 5 种调用形态（`fp.invoke(path,args)(obj)`、
   `fp.invoke(path,args,obj)`、原签名直调等）都没打通，`fp.invoke.length` 为 0
   而 `fp.invoke !== lodash/invoke`。按 VHV 的语义这是 `ineffective`（没测到），
   不是 `fixed`。**没有结论**。
2. **merge 家族这轮被判 `ineffective`，不是 `fixed`。** AST 给出
   `merge -> baseMerge -> assignMergeValue -> baseAssignValue / partial(define-only-proto)`
   —— `baseAssignValue` 的 `defineProperty` 分支只特判 `__proto__`，不管
   `constructor.prototype`。但实测 4.17.20 和 4.18.1 都不污染，原因是
   `Object.prototype` 本身不可写（赋值静默失败）+ 更早的版本已经挡住了
   `merge` 的 `__proto__` 键。**不能把这批 false 算成本次 patch 的功劳。**
3. **`_.result` 确认是无 guard 的调用 sink，但参数不可控。**
   `_.result({}, ['__proto__','__defineGetter__'])` 抛
   `TypeError: Object.prototype.__defineGetter__: Expecting function` ——
   这条错误本身就是证据：它确实走到了 `Object.prototype` 上并以它为 this 调用了该函数，
   只是 `result` 不传参数，所以只能调用零参函数。影响面低于 invoke 家族，
   但「能调到哪个对象」和 invoke 是同一个漏洞。

## 六、下一步（按性价比排）

1. **把 locate.js 泛化到别的库**。当前 sink 名是 lodash 的，但它其实是
   「path → 属性访问/调用」的一类模式。下一个靶子应选**更新频繁但安全审计薄**的
   （npm CLI 工具、配置解析库），而不是第二个巨型工具库。
2. **查真实下游用法**：`_.invoke(` / `.invoke(` 在 npm 生态里 path 是否常来自
   请求参数。这决定报告写「理论影响」还是「可量化影响」。
3. **补 fp 形态**：直接读 `fp/convert.js` 的 rest 参数分支，而不是继续试调用。
4. **报厂商**：现在证据已经足够支撑「4.18.0 的 patch 修了 baseUnset 漏了
   baseInvoke」这个叙述 —— 有 patch 原文、有 AST 对照、有 3 版矩阵、有单体模块
   与 ESM 复现。这是 GitHub Security Advisory 私有通道需要的东西。

## 七、可迁移性验证：换一个库、换一个生态（这节是给「方法论可信」做担保的）

只在一个库上得出「工具好用」是没有说服力的。所以换 `dot-prop` 跑一遍 ——
它和 lodash 同属「按 path 读写对象」家族，但代码结构完全不同（138 行、
`module.exports = {get,set,has,deleteProperty}` 对象字面量导出），
且历史上出过 CVE-2020-8116，**修复前后都拿得到**，正好构成双向校准。

### 实测结果

| 版本 | locate.js 判定 | 手工实测 |
|---|---|---|
| dot-prop **5.1.0**（未修） | 4 个 API 全 `none` | `set({}, '__proto__.x')` → `({}).x === 1`；`constructor.prototype` 同样打穿 |
| dot-prop **6.0.1**（已修） | 4 个 API 全 `validated` | 两个载荷都返回 `undefined`（拦住）；正常 `set/get('a.b.c')` 仍返回 7 |

**判定与实测 100% 一致，且正常功能未受影响。**

### 为了让工具能跑别的库，改了三处（都是「被 lodash 惯坏」的硬编码）

1. **导出识别**原来只认 `lodash.foo = bar`。现在覆盖 `exports.foo` /
   `module.exports.foo` / `module.exports = {get, set}`（含 method shorthand）。
   不改这条，换个库矩阵直接是空的。
2. **sink 集**原来写死 lodash 的内部函数名。现在 `--sinks getPathSegments` 可指定，
   且不在预设三档里的自定义 sink 标 `custom`，仍然进主表 ——
   用户点名的函数不该因为"不在预设表里"被归进只读背景而看不见。
3. **guard 检测**原来只看函数体内有没有 `'__proto__'` 字面量比较。
   dot-prop 把黑名单放在模块顶层 `new Set([...])`，函数里只有一句 `isValidPath(parts)`，
   按旧逻辑会判 `none` —— **这是假阳性，比漏报更危险**。新增「文件级黑名单 + 调用校验器」
   组合判定，但它只给 `validated` 而**不给 `full`**：
   `validated` 是"看起来有校验"，`full` 是"我们逐键确认过拦截逻辑"。
   报告里必须能区分，否则审计时无法复核。

### 这条校准线本身的价值

它把工具的结论从「我的分析说它有问题」变成「同一套分析在已知修好的版本上
会说没问题」。后者才叫阴性对照 —— 没有它，前面所有 `none` 都可能是工具不会看。
