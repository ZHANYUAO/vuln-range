# 第三轮：守卫覆盖率扫描与「修复传播断层」

日期：2026-11-02
工具：`vhv/guardcov.js`（v3）+ `vhv/locate.js`
扫描对象：13 个 path/merge 类库 + 8 个 lodash 单方法包
结论一句话：**没有找到第二个 RCE 级新洞；但找到了一条比洞更难反驳的结构性问题 —— 修复只发到 advisory 点名的那个包。**

---

## 一、这轮换了个问题

前两轮问的是「这个 API 能不能走到危险 sink」（可达性）。这轮问的是：

> 这个库有没有一个**正确**的守卫？它护住了几个点？剩下那几个能不能真打穿？

为什么要单独问：静态扫描器（CodeQL/Semgrep 自定义规则、以及多数论文的判据）看到
`function safeGet(o,k){ if(k==='__proto__') return; ... }` 就判定库安全了。
lodash 的反例说明这不够 —— `safeGet` 存在 8 年，只被 `baseMerge`/`baseMergeDeep` 调用 3 次，
`baseGet`/`parent`/`baseInvoke` 一次都没用过。**锁造好了，只装在一扇门上。**

所以把「守卫的定义数 G」和「守卫的覆盖数 C」拆成两个数来量。

## 二、工具：`guardcov.js`

### 必须支持四种守卫写法（只支持第一种就会大面积误报）

| 形态 | 例子 | 出处 |
|---|---|---|
| `block` | `if (key === '__proto__') return;` | lodash `baseSet` |
| `switch` | `switch(k){ case '__proto__': return }` | jsonpointer `setter` |
| `predicate` | `const isUnsafeKey = k => k === '__proto__' \|\| k === 'constructor'` | set-value |
| `filter` | `parts.filter(blacklistFilter)` + `if (check.length !== parts.length) throw` | dot-object |

**误报比漏报更危险**：v1 只认 `block`，把 `dot-prop` / `set-value` / `dot-object`
三个**已实测能拦**的库全报成 `NO_GUARD`。若不查证就写进报告，整批结论作废。

### 两类汇点必须分开统计

- `path`：沿 `path`/`keys`/`segments` 形参逐段下钻 —— `lodash baseGet`、`dot-prop get`
- `merge`：遍历源对象键 + `target[key] =` —— `deep-extend`、旧版 `merge`

语义完全不同。混在一起会把「merge 有 51 个点全被 ownkey 挡住」算成 path 的覆盖率，
得出「覆盖率很高」的错误结论。

### 校准（先有答案再测工具）

在 lodash 4.18.1 上，工具必须复现手工结论：

| 项 | 手工结论 | 工具输出 | 一致 |
|---|---|---|---|
| 黑名单型守卫 | `baseSet` / `baseUnset` / `safeGet` | 3 个，全部找到 | ✓ |
| `safeGet` 调用点 | 3 处（grep 实测 3654 / 3681 / 3682） | 3 | ✓ |
| `baseGet` 是否覆盖 | 未覆盖 | `L3082 object[toKey(path[index++])]` 未覆盖 | ✓ |
| `baseInvoke` 是否覆盖 | 未覆盖 | `L3263 object[toKey(last(path))]` 未覆盖 | ✓ |
| `result` 是否覆盖 | 未覆盖 | `L13734` 未覆盖 | ✓ |

## 三、批量结果：13 个库

`Gb` = 黑名单型守卫数，`S/U` = 汇点总数/未覆盖数。

| 库 | 版本 | Gb | path S/U | merge S/U | 工具信号 | 实测结果 | 一致 |
|---|---|---|---|---|---|---|---|

| **lodash-es**（单模块） | 4.18.1 | 0 | 1/**1** | — | UNGUARDED | `_baseInvoke` 可 RCE | ✓ |
| dot-prop | 6.0.1 | 2 | 4/0 | 0/0 | COVERED | `__proto__` 与 `constructor.prototype` 都拦住 | ✓ |

| dset | 3.1.4 | 1 | 0/0 | 0/0 | NO_SINK | 拦住（导出形态修正后） | 工具失效① |
| just-safe-set | 4.2.1 | 1 | 4/0 | 0/0 | COVERED | 抛 `not supported` | ✓ |

| **get-value** | 4.1.0 | 0 | 3/**3** | 0/0 | NO_GUARD | **可拿 `Function`** | ✓ |
| flat | 6.0.1 | 2 | 7/0 | 0/0 | PARTIAL_KEYS | 4 种载荷全未命中 | ✓ |

### 工具失效的三个场景（必须写明，否则会误读结果）

1. **minify**：`dset` 的 `dist/index.js` 是压缩产物，形参被压成单字母，
   `pathWalker` 判不出「路径语义形参」，`S=0`。工具说没问题 ≠ 没问题。
2. **`Object.keys().forEach` 而非 `for..in`**：`deep-extend` 用
   `Object.keys(obj).forEach(function(key){ target[key] = ... })`，
   我原来的 merge 汇点判据只认 `for..in`，整个汇点被漏掉。
3. **主文件是纯再导出**：`lodash-es/lodash.js` 只有 331 行 `export { default as x } from './x.js'`，
   扫主文件得到「0 个函数、NO_SINK」。必须落到 `_baseGet.js` / `_baseInvoke.js` 这类单模块。

**共同点：这三种都不是「库安全」，而是「工具看不见」。** 命中与否必须由运行时 marker 决定。

### 一条必须自纠的旧结论

上一轮我记的是「jsonpointer 5.0.1 三键全拦」。**这是错的。**

```js
jp.get({}, '/constructor')  // → fn Object      ← 穿出去了
jp.set({}, '/__proto__/x')  // → 抛错（拦住）
```

`jsonpointer` 只给 `set` 装了守卫（`setter`，L16），`get`（L73）完全没有。
它之所以没到 RCE，是因为循环里有一句与安全无关的 `typeof obj !== 'object'` —— 
函数不是 `'object'`，走一步就 `return undefined`。**是巧合，不是防护。**

危害定级：能读到 `Object` 与 `Object.prototype`，但没有调用原语（无 invoke 类 API），
所以是**信息暴露**，不是 RCE。按 RCE 报会被一击打回。

### 半覆盖但不是漏洞

`flat` 的守卫只查 `__proto__`、不查 `constructor`，工具标 `PARTIAL_KEYS`（7 个点）。
但实测 4 种载荷都没打穿：`unflatten` 把每一段都建成**自有属性**，
`constructor` 被同名的自有属性遮蔽，走不到 `constructor.prototype`。

**「守卫只挡一半」是代码味道，不是漏洞。** 这两者必须分开写。

## 四、真正的发现：修复传播断层

这条比再多一个载荷有价值，因为它可被独立复核。

`lodash` 主包 4.18.0（2026-04-01）修了 `_.unset` / `_.omit`。按方法拆分的独立包状态如下：

| 包 | 版本 | 最后发布 | 周下载 | OSV advisory | 工具（path S/U） | 实测 |
|---|---|---|---|---|---|---|
| lodash | 4.18.1 | 2026-04-01 | 206,478,795 | 10 | — | 基线 |
| **lodash.get** | 4.4.2 | **2016-08-13** | **22,320,171** | **0** | 1/**1** | 返回 `Function`，`Function('return "OK"')()` → `OK` |
| **lodash.invoke** | 4.5.2 | **2016-08-13** | 33,215 | **0** | 2/**2** | `invoke({}, P, 'return "VHV_x"')()` → **直接执行** |
| **lodash.set** | 4.3.2 | **2016-08-13** | 2,486,654 | 1 | 3/**3** | `set({}, ['__proto__','x'], 1)` → **污染成立** |
| lodash.has | 4.5.2 | 2016-08-13 | 1,638,972 | 0 | 1/0 | 返回 `false`，未穿 |
| lodash.at | 4.6.0 | 2016-08-13 | 143,579 | 0 | 1/**1** | 返回 `Object.prototype`，未到 `Function` |
| lodash.result | 4.5.2 | 2016-08-13 | 40,155 | 0 | 1/**1** | 返回 `{}`，未 RCE |
| **lodash.unset** | **4.18.0** | **2026-03-31** | 204,114 | 2 | 2/1 | 危险键被拦住 —— **唯一被更新的包** |

### 三个可独立复核的事实

1. **七个独立包里，只有 `lodash.unset` 在 4.18.0 发布日前后更新过**
   （2026-03-31），其余六个全部停在 **2016-08-13**。
   发布日期与 advisory 完全对应：advisory 说的是 `_.unset`/`_.omit`，所以只发了 `lodash.unset`。
   **发布策略 = advisory 点名哪个就发哪个，不是"把修复同步到所有分发形态"。**

2. **`lodash.get@4.4.2` 周下载 22.3M，OSV advisory 数为 0。**
   它能返回 `Function` 并执行任意代码，而没有任何 advisory 覆盖这个包名。
   按"有没有 advisory"判断安全性的自动化工具（含 OSV-Scanner、npm audit 的打分逻辑），
   在这里会给出**无风险**的结论。

3. **连唯一拿到补丁的 `lodash.unset@4.18.0` 内部仍留着无防护的 `baseGet`**

   ```
   guards: baseUnset@585(blacklist-one), isKeyable@716(blacklist-one)
   未覆盖: L486  baseGet | object[toKey(path[index++])]
   ```

   补丁是**点对点修函数**（在 `baseUnset` 里加判断），不是修通道。
   只要还有别的 API 走到 `baseGet`，这条路就一直是开的。
   这与第二轮的结论完全一致，并且在一个"已经修好的包"里再次出现。

### 危害定级

- `lodash.get` / `lodash.invoke`：一旦调用方的 path 可控，**直接 RCE**。
  但同样受限于「path 必须用户可控」这一前置条件，暴露面远小于 `merge(obj, req.body)` 类。
- `lodash.set@4.3.2`：可直接污染，但 **CVE-2020-8203 的 `last_affected` 就是 4.3.2**，
  属"已知、且官方从未修"。不是新发现，不能算这轮的产出。
- 三者都**不是**凭空 0day：根因与第二轮同一个（`baseGet` 无穿越守卫），
  新的是「独立包分发形态从未被修复触及」这个**传播层面**的事实。

## 五、这轮我错了三次，都是同一类

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| 1 | `guardcov` 只认 `block` 形态守卫 | dot-prop / set-value / dot-object 三个已实测安全的库被报 `NO_GUARD` | 补 `predicate` / `filter` 两形态 + 实参引用作调用边 |
| 2 | 调用点按「函数包含该调用」归属 | 包裹全文件的 IIFE 被算成所有守卫的调用者，`safeGet` 显示 5 次（真值 3 次） | 单遍 DFS + 函数栈，只归属最近闭包 |
| 3 | `baseUnset` 只取第一处判据 | 完整防护被误判成半修复，100 个站点被标 keys 不全 | 聚合函数内全部判据的键集 |
| 4 | `dset` 导出是 `{dset}` 不是函数 | 三个用例全报 `dset is not a function`，若不做对照会记成"安全" | `typeof m==='function'?m:(m.default\|\|m.dset)` |

第 4 条是**同类事故第三次**（前面是 `get-value` 的 `{default}`、以及判据方向那次）。

> **铁律补充：任何"没命中"必须先排除装置故障。** 判据是：
> 该库的正常功能对照必须同时跑通；跑不通 = 装置坏了，不是库安全。

## 六、这轮的方法论增量

原来只有「一个库、一个补丁、一个变体」。这轮把它扩成了三张可复用的表：

1. **守卫形态表**（4 种写法）—— 决定工具能覆盖多少库。
2. **覆盖矩阵**（守卫 × 汇点 × 键）—— 把"有没有守卫"变成"护住了几个点、挡了几个键"。
3. **分发形态表**（主包 / 单模块 / 单方法包 / ESM / fp）—— 这轮证明**这才是最容易被忽略的一维**。

第 3 张表是新的，也是这轮唯一真正的新发现所在：
**同一个修复在同一个项目里，可以只存在于一种分发形态中。**

## 七、下一步（按边际收益排序）

| 优先级 | 事项 | 为什么 |
|---|---|---|
| P0 | 把 `lodash.get` / `lodash.invoke` 写进披露报告（与主包合成一份，用「分发形态矩阵」作为主论据） | 22.3M/周 + 0 advisory + 可 RCE，是本轮最硬的组合 |
| P1 | 把「分发形态」变成自动检查：对任一 npm 包枚举 主包/`lodash.X` 拆分包/`-es`/`/fp`，逐个跑同一组载荷 | 这轮是手工发现的，应做成工具；可迁移到任何多形态发布的库 |
| P2 | 修工具的三个盲区（minify 检测、`forEach` 键遍历、再导出主文件） | 现在这三类会静默给出 NO_SINK，属于"假阴性来源" |
| P3 | 换生态：Python 的 `dotty`/`glom`/`python-box`，Go 的 `gjson`/`sjson` | 验证「分发形态断层」是不是 npm 特有 |

**不建议做的**：继续在 lodash 主包里加载荷（已挖尽）、把 `flat` 的半覆盖报成漏洞、把 `lodash.set` 当新发现（CVE-2020-8203 已覆盖）。
