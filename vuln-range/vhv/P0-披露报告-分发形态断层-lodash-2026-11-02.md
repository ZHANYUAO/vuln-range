# 披露报告：lodash 路径取值族的分发形态断层

**组件**：`lodash` 4.18.1 / `lodash.get` 4.4.2 / `lodash.invoke` 4.5.2 / `lodash-es` 4.18.1 / `lodash/at`
**类别**：CWE-1321（原型污染，**只读取不写入**的子类）/ CWE-94（代码注入）
**报告人**：独立研究
**日期**：2026-11-02
**状态**：草案，未提交
**证据**：`cases/poc-disclosure.json`、`cases/distcheck-lodash.json`、`cases/distcheck-lodash.md`

---

## 一、一句话

`_.get(obj, path)` 系列 API 允许 `path` 穿越原型链读到 `Function` 构造器，从而在**不写入任何对象**的情况下执行任意代码；而这个语义在 lodash 主包与三个独立发版的兄弟包中**十年前后完全一致**，生态里 **22,320,171 次/周**的装机量对应 **0 条 advisory**。

### 2.2 「0 advisory」的准确含义（防止被误读）

这不等于「lodash.get 漏掉了某个历史 CVE 的修复」。准确表述是：

- lodash 家族的历史 CVE 影响范围从来只标注 `lodash` 主包（以及少数 `lodash.merge` / `lodash.defaultsdeep`）；
- `lodash.get` / `lodash.invoke` **没有任何 advisory 认领过它们**，因此它们既不在「受影响版本列表」里，也不在「已修复版本列表」里；
- 结果是：这两个包自 2016-08 后再没收到任何更新，其内联的 `baseGet` 副本保持 2016 年形态；
- 而主包的 `_.get` 同样从未针对此语义做过修改 —— **两边一样旧，只是一个被 advisory 体系看见了，一个没有。**

对比 `lodash.set`：主包在 4.17.17 修了写侧（CVE-2020-8203 相关），`lodash.set@4.3.2` 至今仍可打穿（见 5.3 节矩阵）。**这才是「断层」二字的实证**——不是推测，是同一份载荷在主包被拦、在兄弟包打穿。

### 2.3 兄弟包「集体冻结」的统计证据

把 18 个 `lodash.*` 兄弟包的最后发版日排在一起（`registry.npmjs.org`，2026-11-02 实测）：

| 最后发版日 | 包 | 数量 | 说明 |
|---|---|---|---|
| **2016-08-13** | `get` `invoke` `set` `at` `has` `result` `method` `methodof` `clonedeep` `assign` `pick` `camelcase` | **12** | **拆分单体包的那一天，之后再没动过** |
| 2017-01-10 | `isequal` | 1 | |
| 2019-07-10 | `merge` `defaultsdeep` | 2 | **正是 CVE-2019-10744 的修复版本 4.6.2 / 4.6.1** |
| 2026-03-31 | `unset` `omit` | 2 | |
| 2026-04-01 | `template` | 1 | |

这张表是本报告最重要的单张证据，它说明三件事：

1. **冻结是常态**：18 个包里 12 个（66.7%）停在同一天 —— 2016-08-13。
2. **解冻只发生在被点名时**：唯一一批「非最近」的更新是 2019-07-10 的 `lodash.merge` / `lodash.defaultsdeep`，而这两个包正是 CVE-2019-10744 的受影响包。**advisory 点名之前，它们和其他兄弟包一样冻结；点名之后，它们被单独捞出来修了。**
3. **`lodash.get` 从未被点名**，所以它不需要修 —— 在现有机制里，它甚至不算"漏修"，因为压根没有"该修"的记录。

这就是「修复传播断层」的物理形态：**不是维护者失职，是机制只对"被写入 advisory 的包名"作出反应。**

## 三、技术原理：三跳，零写入

### 3.1 载荷

```js
const _ = require('lodash');                      // 或 require('lodash.get')
const F = _.get({}, ['__proto__', 'constructor', 'constructor']);
//      ^ 返回 Function 构造器，全程没有写过任何对象的任何属性
F('return process.version')();                    // → "v22.22.2"
```

单行版本：

```js
_.invoke({}, '__proto__.constructor.constructor', 'return process.version')()
```

### 3.2 为什么这与「原型污染」不是一回事

| | 原型污染（CWE-1321 主流形态） | 本例 |
|---|---|---|
| 前置条件 | 必须先有一次**写入**（`Object.prototype.x = ...`） | 无需任何写入 |
| 检测手段 | 比对 `Object.prototype` 是否被污染 | **现有检测手段全部失效** |
| 污染面残留 | 全局，进程内所有对象可见 | **零残留**，一次调用后无痕 |
| 危险前提 | 需存在 gadget 把被污染键用起来 | 读取动作**本身就是** gadget |
| 典型 API | `_.merge` / `_.set` / `_.defaultsDeep` | `_.get` / `_.invoke` / `_.at` / `_.method` |

关键代码在 `lodash.js` 的 `baseGet`：

```js
function baseGet(object, path) {
  path = castPath(path, object);
  var index = 0, length = path.length;
  while (object != null && index < length) {
    object = object[toKey(path[index++])];   // ← 不区分 own / 继承，也不校验键名
  }
  return (index && index == length) ? object : undefined;
}
```

`{}` → `__proto__` 命中 `Object.prototype` → `constructor` 命中 `Object` → `constructor` 命中 `Function`。
零写入、零污染、零残留。用户传给 `_.get` 的 `path` 一旦可控，就是一条直达 `Function` 的通道。

### 3.3 为什么 8 年的修复都没碰到它

lodash 里确实存在正确实现，但它只装在写侧的门上：

| 守卫位置 | 函数 | 行（4.18.1） | 保护的操作 |
|---|---|---|---|
| 1 | `baseSet` | ~4040 | 写 |
| 2 | `baseUnset` | ~4393 | 删 |
| 3 | `baseUnset` | ~4399 | 删 |
| 4 | `safeGet` | ~6705 | 仅被 `baseMerge` ×1 / `baseMergeDeep` ×2 调用 |

`safeGet` 是全库唯一的「安全取值」实现，存在 8 年，调用点 3 个，全部在 merge 家族内部。`baseGet`、`parent`、`baseInvoke`、`result` —— **一次都没调用过它**。

锁造好了，只装在一扇门上。这是本报告第二个结构性论点。

### 4.2 矩阵读法：三种形态，三种含义

1. **全形态打穿**（get / invoke / at / method / methodOf）
   → 说明这不是「某个包的实现疏忽」，而是**语义层面从未被修复**。修一个包没有意义。

2. **判定分裂**（set：主包挡住、`lodash.set@4.3.2` 打穿）
   → 说明修复**确实发生过**，但只发到了 advisory 点名的那个包。兄弟包是独立 npm 包、独立发版周期、独立维护者视角，**永远不会收到主包的修复**。这是"断层"的物理机制。

3. **全形态挡住**（unset）
   → 说明矩阵有区分力，不是所有格子都红。阴性对照成立。

### 4.3 为什么「分发形态」应该成为攻击面建模的一个维度

现有 SCA 工具（npm audit / Dependabot / OSV-Scanner / Snyk）的判定链是：

```
package.json 里的包名  →  advisory 的 affected 列表  →  版本区间比较
```

这条链在不同分发形态下会给出三种错误结论：

| 用户实际引入的形态 | SCA 看到的名字 | 实际代码来源 | SCA 结论 | 真实情况 |
|---|---|---|---|---|
| `require('lodash.get')` | `lodash.get` | 独立副本（2016） | 「无已知漏洞」 | 可 RCE |
| `require('lodash/get')` | `lodash` | 主包 `_baseGet.js` | 「4.18.1 已修复」 | **仍可 RCE** |
| `import {get} from 'lodash-es'` | `lodash-es` | 独立 ESM 构建 | 「跟随主包」 | **仍可 RCE** |

第二行尤其值得注意：**SCA 说"已修复"，是因为它以为你在用主包，而主包的修复点在写侧，根本没触及 get。** 这不是工具漏报，是「修复点 ≠ 报告点」的结构性错配。

## 六、建议修复

### 6.1 最小修复（2 行，已验证）

`baseGet` 的循环体：

```diff
 while (object != null && index < length) {
-  object = object[toKey(path[index++])];
+  var key = toKey(path[index++]);
+  if (key === '__proto__' || (key === 'constructor' && typeof object[key] === 'function')) {
+    return undefined;
+  }
+  object = object[key];
 }
```

判定依据：
- `__proto__` 一律拒绝（无正当业务会读它）；
- `constructor` 只在**取到的是函数**时拒绝 —— 保留 `_.get(obj, 'constructor.name')` 这类合法用法（返回字符串时放行）。

实测结果（`src/lodash-fix`）：全部载荷失效，对照组全部通过，17/17 功能回归测试无破坏。

> 但这是**最小修复，不是最优修复**。真正的语义修复应该是「只沿 own property 下钻」或「提供显式的 `allowInherited` 开关」，因为代码里仍存在其他可继承路径（如 `__defineGetter__`、`valueOf`）。2 行修复的价值在于：**能在不改 API 契约的前提下立刻止血**，适合作为披露时的默认建议。

### 6.2 需要一并覆盖的分发形态

修复必须同时发到：

- `lodash`（`_baseGet.js` / `lodash.js` 内联副本）
- `lodash-es`
- `lodash.get`（**关键：独立仓库、独立发版、2016 年后未更新**）
- `lodash.invoke`
- `lodash.at`、`lodash.method`、`lodash.methodOf`
- 以及 `lodash/fp/*` 的映射层（`_mapping.js`，`invokeArgs → invoke`）

只改主包 = 只修了 5 个形态里的 3 个。

## 七、真实世界可达性（实测，不是估计）

**必须说清楚的前提**：本漏洞要求应用把**攻击者可控的值**当作 `path` 传给 `_.get` / `_.invoke` / `_.at`。

我们把这条前提拿去实测了，而不是停在"理论上可控"。结果对我们不完全有利，但它是真的：

### 7.1 测量

| 项 | 值 |
|---|---|
| 目标 | 8 个主流 Node 应用（parse-server、`@directus/api`、`@strapi/core`、`@strapi/utils`、`@nocobase/server`、apostrophe、n8n、ghost） |
| 覆盖架构 | REST / GraphQL / 低代码 / CMS 四类 |
| 源文件 | 6,457（含 73 个 minified 排除） |
| lodash path 调用点 | 588 |
| 非字面量 path | 314 |
| **可追溯到请求数据的** | **2** |
| 经人工核查成立的 | **0** |

两处候选的核查结论：

- **apostrophe** 的 `_.has(self.options.apiKeys, req.query.apikey)` 是真正的鉴权分支，key 完全可控。但它用的是 `_.has`——该函数在 4.17.11 已加 own-property 判定（CVE-2020-8203），`_.has(obj,'__proto__')` 返回 `false`，分支不可达。
- **directus** 的 GraphQL 查询降级确实会穿越（`parent` 来自用户可控的 alias），但 alias 语法每段只能是单个 `Name`，且 `Object.prototype` 无可枚举自有属性，穿越后无效果。

### 7.2 为什么这么低

314 处里 237 处 path 来自常量或 schema 派生。抽样看几乎全是三类：输出字段白名单（`_.pick(data, ALLOWED_READ_FIELDS)`）、数据库/内容模型列名（`_.get(data, attributeName)`）、部署配置路径。

**`_.get` 在现代应用里的实际角色是"按 schema 声明取值"，不是"按用户给的路径取值"。** 这个用法结构上免疫本缺陷。

### 7.3 所以本报告主张什么、不主张什么

| 主张 | 是否成立 |
|---|---|
| 库层存在 path 穿越原语，且 8 年未被修复 | ✅ 已实测 |
| `lodash.get` 等兄弟包停留在 2016 代码且 0 advisory | ✅ 已实测 |
| 攻击者可控 path 时可达 RCE | ✅ 已实测（本机） |
| **主流应用普遍暴露此路径** | ❌ **实测否证（0/8）** |

我们主动把最后一条写进来。原因很实际：维护者最可能的驳回理由就是"实际不可达"，与其被对方说出来，不如我们先说，并附上我们自己的测量。这样剩下的讨论才是关于**修复**，而不是关于**危害是否存在**。

### 7.4 仍然成立的场景（我们不否认，只是未能实测命中）

```js
// 1. 字段投影：用户指定要取哪些字段（且未做白名单）
req.query.fields.split(',').forEach(f => out[f] = _.get(row, f));

// 2. 规则引擎 / DSL：路径来自用户可编辑的规则配置
_.get(ctx, rule.path)

// 3. 通用取值 API：把 path 直接透传
app.get('/api/value', (req, res) => res.json(_.get(store, req.query.p)));

// 4. JSONPath / GraphQL 适配层：把外部路径语法翻译成 lodash path
```

第 4 类是下一步最该测的：我们测的是**应用**，不是**适配层**。适配层正是"用户路径"停止变成"schema 键"的那个位置。

### 7.5 定级

CVSS `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H`，**High**，不宣称 Critical。`AC:H` 现在有了实测支撑：8 个应用里 0 命中，说明这个前提确实不容易满足。

| 3 | GitHub Advisory Database | 申请 GHSA，请其覆盖兄弟包 | 待发 |
| 4 | OSV | 随 GHSA 自动同步 | — |
| 5 | npm 安全团队 | 若兄弟包无人维护，请求 deprecate 或转让 | 待发 |

**为什么合并成一份而不是拆成三份**：拆开后，主包维护者会以「`_.get` 的既有语义」为由拒绝，兄弟包会以「主包没修」为由拒绝。合并报告的核心论据就是**矩阵本身**——它同时证明「主包也没修」和「兄弟包永远收不到修复」，把责任从「某个包」上移到「分发机制」。

### C. 已知未验证项（不得在披露中宣称）

1. **真实应用命中率**：尚未在任何真实开源应用中验证「path 确实可控」。这是本报告最大的缺口。
2. **其他可继承危险键**：`__defineGetter__` / `valueOf` / `toString` 的可利用性未系统测试。
3. **`lodash/fp/result` 与 `lodash/fp/has`**：矩阵中标记为「未判定」（签名不兼容），**不能当作安全**。
4. **兄弟包维护者归属**：`lodash.get` 是否仍由 lodash 团队维护，未核实。
