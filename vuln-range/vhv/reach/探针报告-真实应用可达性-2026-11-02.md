# 真实应用可达性探针 · 8 个 Node 应用实测

日期：2026-11-02
工具：`scan.js`（AST 定位 + 污点来源分级）、`propagate.js`（跨过程传播）
数据：`cases-apps-trace.json`、`cases-apps-prop.json`、`raw/meta/*.json`

---

## 0. 一句话结论

**在 8 个主流 Node 应用的 6457 个源文件、588 处 lodash path 调用中，只有 2 处的 path 参数可追溯到 HTTP 输入，且两处经人工核查均不构成可利用漏洞。**

这意味着论文里 §5.4 原本要写的「应用级可达性」证据，**方向上被证伪了**：`_.get(obj, userControlledPath)` 这种写法在现代框架里几乎不存在。

但探针换回来一个更值钱的东西——见 §5。

## 1. 先说清楚：头部库这条路为什么走不通

之前扫描 npm 头部 900 个包，完整抓到 872 个元数据：

| 指标 | 值 |
|---|---|
| 已抓元数据 | 872 |
| 依赖 lodash 家族（含 dev/peer） | 29 |
| 其中 runtime 依赖 | **19（2.2%）** |
| 总解包体积 | 47.4 MB |

而 lodash 主包周下载 **2.06 亿**。这个 100 倍的反差只有一个解释：**lodash 的装机量来自传递依赖和存量应用，不来自当前头部库**。所以「扫 Top 500 找真实调用」从采样上就不成立，必须换成直接扫应用。

## 2. 探针设计

### 2.1 目标选择

先查 registry 元数据筛掉不依赖 lodash 的，避免几 GB 无效下载。18 个候选里 8 个命中：

| 应用 | 版本 | lodash 依赖 | 解包 | JS 文件 |
|---|---|---|---|---|
| parse-server | 9.10.7 | lodash | 6.2 MB | 199 |
| @directus/api | 41.0.0 | lodash-es | 2.2 MB | 824 |
| @strapi/core | 5.60.0 | lodash | 5.5 MB | 458 |
| @strapi/utils | 5.60.0 | lodash | 1.5 MB | 152 |
| @nocobase/server | 2.2.37 | lodash | 790 KB | 96 |
| apostrophe | 4.34.0 | lodash | 9.1 MB | 339 |
| n8n | 2.45.7 | lodash | 29.7 MB | 2223 |
| ghost | 6.73.0 | lodash | 31.9 MB | 2166 |

**为什么用 npm tarball 而不是 GitHub**：GitHub 主站本机超时；codeload 虽通但 monorepo zip 数百 MB 且含大量非运行时代码。tarball 是「实际被安装的那份」，作为可达性证据更贴切。

### 2.2 判定分四级，而不是有/无

这一步是整个探针的关键。只判「path 是不是字面量」会得到 314 个候选，人工核不完；而它们的可达性天差地别。

| 级别 | 含义 | 例 |
|---|---|---|
| `http` | 初始化表达式里出现请求对象或 HTTP 语义属性 | `_.get(o, req.query.field)` |
| `param` | 是函数形参，来源要看调用方 | `function f(path){ _.has(r, path) }` |
| `maybe` | 只出现 `.data/.fields/.url` 这类弱信号 | `_.pick(frame.data, x)` |
| 无源 | 常量、schema、模块级配置 | `_.pick(o, ALLOWED_READ_FIELDS)` |

`param` 再用 `propagate.js` 跨过程升/降级。

### 3.3 两个候选逐一核查

**候选 A：apostrophe `modules/@apostrophecms/express/index.js:350`**

```js
const key = req.query.apikey || req.query.apiKey || getAuthorizationApiKey();  // 完全可控
if (_.has(self.options.apiKeys && self.options.apiKeys, key)) {
  const info = self.options.apiKeys[key];
  if (info.role === 'admin') { taskReq = self.apos.task.getReq(); }   // 管理员
```

这是货真价实的鉴权分支，`key` 直接从 query 取。**实测判定为不成立**：

```
_.has(apiKeys, '__proto__')   = false
_.has(apiKeys, 'constructor') = false
_.has(apiKeys, 'toString')    = false
```

`_.has` 用的是 `hasPath` + `hasOwnProperty`，**不穿继承**（CVE-2020-8203 的修复）。所以 `__proto__` 走不进 if 分支，返回 403。

**候选 B：directus `dist/services/graphql/schema/parse-query.js:54`**

```js
setDeep(query.deep, path, merge({}, get(query.deep, parent), { _alias: {...} }));
```

`parent` 追溯上去是 GraphQL selection 的 alias（`selection.alias.value`），攻击者确实能控制。但：

1. GraphQL 的 alias 必须是合法 `Name`（`/[_A-Za-z][_0-9A-Za-z]*/`），不能含 `.`，所以只能构成路径**单段**；
2. `get(query.deep, '__proto__')` 返回 `Object.prototype`，随后被 `merge({}, Object.prototype, {...})` 合并——而 `Object.prototype` 没有可枚举自有属性，结果等同于 `{_alias: ...}`；
3. 目标对象 `query.deep` 由 `Object.create(null)` 创建，本身无原型链。

**判定：能穿越，但无效果。**

## 4. 「可达性低」这个结论，我先证伪了自己的工具

这是本轮最重要的过程记录。扫描过程中**连续三次**出现「某包 0 命中」，每次都差点被当成「该应用不用 lodash」。

| # | 现象 | 真因 | 修法 |
|---|---|---|---|
| 1 | nocobase 96 文件，0 命中 | esbuild 产物 `import_lodash = __toESM(require("lodash"))`，init 是包装函数调用不是 `require` | `requireTarget()` 递归剥 `__toESM` / `_interopRequire*` / `__importDefault` / `__importStar` |
| 2 | n8n 2223 文件，0 命中 | tsc 产物 `get_1.default(obj, p)`——方法名被 `.default` 挡在中间 | callee 分支允许 `X.default` → 取 `X` 的 member 绑定 |
| 3 | 修完上一条，n8n **仍然** 0 命中 | tsc 把 ESM import 编译成 `(0, get_1.default)(obj, p)`，callee 是 `SequenceExpression` | 剥 `SequenceExpression` 取最后一个表达式 |

三次修复都补了对应 fixture（`fixtures/pkg3`、`fixtures/pkg4`），含正例与对照：

| fixture | 正例 | 对照 |
|---|---|---|
| pkg3 `bundled.js` | `__toESM(...).default.get`、`_interopRequireDefault(...).default.omit`、`__importStar(...).default.set`、`require('lodash').get` | 字面量 path、非 lodash 模块的同形调用 |
| pkg4 `importdefault.js` | `get_1.default(obj,p)`、`pick_1.default`、`set_1.default` | `chunk_1.default(arr,n)`（第二参数是 size 不是 path） |
| pkg4 `indirect.js` | `(0, lodash_1.default.get)(obj,p)` | 字面量 path |

修复后 n8n 从 0 变成 30 个调用点 / 19 tainted。

**如果没有这一步，报告里的「n8n 不用 lodash」会是一个彻头彻尾的错误结论。**

另外还修了一处逻辑串味：`_.each(columns, function each(columnKey){...})` 的回调形参被按同名函数反查到了另一个 `_.each(context, ...)` 调用点，把数据库列名误判成 HTTP 输入（ghost）。修法是记录「作为实参传入的函数起始行」，回调一律不按名字反查。

## 5. 探针换回来的东西：同一个鉴权判断，`has` 安全、`get` 可被击穿

apostrophe 那处虽然不成立，但它暴露了一个比「找到一个洞」更值得写进论文的现象。

同一段鉴权代码，只把 `_.has` 换成 `_.get`（lodash 4.18.1 实测）：

| 表达式 | 结果 |
|---|---|
| `_.has(apiKeys, '__proto__')` | `false` |
| `_.get(apiKeys, '__proto__')` | `Object.prototype`（对象） |
| `_.get(apiKeys, '__proto__').role` | `undefined` |
| **先有原型污染 `Object.prototype.role='admin'`** | |
| `_.has(apiKeys, '__proto__')` | 仍然 `false` |
| **`_.get(apiKeys, '__proto__').role`** | **`'admin'`** |

也就是说：

- 开发者写 `_.has` → 安全，且**他自己不知道为什么安全**；
- 写 `_.get` → 单看无害，但一旦系统任意位置存在原型污染，这段鉴权立刻被放大成**管理员冒用**；
- 两个函数在文档里都是「检查 / 读取属性」，语义差异**没有任何提示**。

这解释了我们前几轮发现的完整链条：`has` 在 4.17.11 被修（CVE-2020-8203），`get` 至今没修。**修复只落到了被 advisory 点名的那一个函数上，兄弟函数的语义分歧被原样保留。** 这正是「分发形态断层」在函数粒度上的同构现象。

## 6. 为什么可达性这么低：结构性原因

314 个 tainted 里 237 个「无源」，人工抽样看，path 几乎全部来自三类：

| 来源 | 典型写法 | 为什么不吃外部输入 |
|---|---|---|
| 输出字段白名单 | `_.pick(data, ALLOWED_READ_FIELDS)` | 白名单由 API 定义，是安全边界本身 |
| 数据库/内容模型 schema | `_.get(data, attributeName)`、`_.has(model.changed, columnKey)` | 列名来自 schema 定义 |
| 配置路径 | `_.get(self.options, dotPath)`、`_.get(userPluginsConfig, \`${name}.config\`)` | 由部署者填写 |

**lodash.get 在现代应用里的实际角色不是「按用户给的路径取值」，而是「按 schema 声明取值」。** 这个用法天然不接受任意 path——这也是为什么 8 个大应用一个反例都没有。

反过来说，只有当某个框架把「用户输入」直接当路径用时才会出洞，而现代框架普遍用 schema 校验（strapi 的 sanitizers、directus 的 AST 重写）把这一步挡住了。

## 7. 对论文与披露的影响

### 7.1 必须改的

论文 §5.4 原计划写「扫描 Top 500 找可达调用」，现在数据否掉了它。改成：

> 我们在 8 个主流 Node 应用（合计 6457 文件、588 处 path 调用）中测量 path 参数的可达性，发现 314 处非字面量调用中仅 2 处可追溯到请求数据，且均因下游语义不成立。**该原语在应用层的可达性远低于其在库层的普遍性。**

这个负面结果对论文是**加分**而不是减分：它把「库里有问题」和「应用有漏洞」之间的鸿沟量化了，而不是含糊带过。审稿人最常问的正是这一条。

### 7.2 新增的一节

§5.5 写 `has`/`get` 语义分歧 + 原型污染的放大效应。这是本轮唯一的**正向**发现，且有可复现实测。

### 7.3 披露报告要加一句限制

P0 披露报告里「可 RCE」的成立前提是**攻击者能控制 path**。现在有了量化证据：这个前提在主流框架里**罕见但非零**。披露时应主动写出这一点，否则会被维护者用「实际不可达」一句话驳回——而这恰恰是我们自己测出来的。
