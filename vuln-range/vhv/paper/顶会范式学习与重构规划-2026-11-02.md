### 1.2 逐节功能拆解

#### Abstract（240 词，五句话）

1. **重要性**：BAC 是 OWASP Top 10 常年第一。
2. **后果**：绕过访问控制 → 未授权操作 → 数据泄露。
3. **转折**（关键句）：*"Despite substantial attention given to BAC vulnerabilities, effective and reliable approaches to detecting these issues remain limited."*
4. **方法 + 差异**：不同于只查未授权读的响应相似度 oracle，BACScan 提出 feedback-driven oracle。
5. **数字**：20 个应用、89 个漏洞、54 个未报告、35 个 CVE。

**注意第 3 句的句式**：`Despite substantial attention given to X, effective and reliable approaches to Y remain limited.`
这是顶会摘要最标准的转折模板。我们现在的摘要没有这个转折，直接就开始讲自己的发现。

#### 1 Introduction

结构是**四段式**：

| 段 | 内容 | 作用 |
|---|---|---|
| 1 | 行业地位（OWASP 数据）+ 真实案例（Amazon/PayPal/Twitter/TikTok） | 建立外部权威性 |
| 2 | **转折**：虽然研究很多，问题反而更严重 | 制造张力 |
| 3 | 现有方法的路线盘点（白盒 vs 黑盒）→ 选定黑盒 → 深入分析黑盒 oracle | 收窄战场 |
| 4 | 指出 oracle 的**错误假设**（不是"效果不好"） | 致命一击 |
| 5 | 两个挑战 C1/C2 | 预告结构 |
| 6 | 我们的方案 + 评估数字 | 兑现 |
| 7 | 三条 contribution bullet | 收尾 |

**最值得学的是第 2 段和第 4 段的写法。**

第 2 段原文：
> Although BAC vulnerability detection is a well-explored research topic, the increasing severity of BAC vulnerabilities highlights the long-lasting lack of highly effective detection techniques.

这句话同时做了三件事：承认前人工作（不冒犯）、指出领域失败（有张力）、为自己开位置（有必要性）。

第 4 段是**全篇的支点**：
> Unfortunately, the response-based oracle is based on **a flawed assumption**: the direct response to a BAC attack request always provides evidence indicating whether the exploit is successful or not.

它没有说"现有工具准确率低"，而是说"现有工具的**前提假设错了**"。前者是工程问题，后者是科学问题。**顶会要的是后者。**

#### 2 Problem Statement（2 页）

四小节，逻辑链严格：

- **2.1 定义**：BAC 是什么（引 CWE-284 + Figure 1 威胁模型图）
- **2.2 现有技术**：白盒为什么不行（误报高、无法生成 PoC、语言绑定）→ 黑盒为什么行 → 黑盒的三步流程
- **2.3 缺陷**：**先把 BAC 分成 RBAC / MBAC 两类**，再说 oracle 只对 RBAC 有效，对 MBAC 无效。然后给数字：**FP 高达 70.97%，FN 高达 86.96%**
- **2.4 双例对照**：Figure 2(a) 一个假阴性（WeBid）、Figure 2(b) 一个假阳性（SuperMarket）

**2.3 的"分类切割"是整篇论文最聪明的一步。**

在它之前，"BAC 检测"是一个大而模糊的问题，已有工具"大致能用"。
一旦切成 RBAC（读）和 MBAC（改），旧 oracle 的适用范围就被压缩到一半，而且**恰好是被研究充分的那一半**。剩下那一半成了无人区，也就是他们的地盘。

**这个手法我们可以直接复制**：把"原型链问题"切成 **写侧污染（pollution）** 和 **读侧穿越（traversal）**。前者被研究透了（USENIX'23 Silent Spring、各大扫描器），后者无人建模。我们的稿子已经有这个切割（§2.2 表格），但**没有把它放在"立论核心"的位置**，只是当成背景介绍。

**2.4 的双例对照也值得注意**：一个假阴 + 一个假阳，两个方向都演示。只举假阴，读者会问"那你是不是只会抓漏"；只举假阳，读者会问"那真漏洞你抓得到吗"。**一正一反，堵住两个质疑。**

#### 3 Overview（1.5 页）

三段式，非常干净：

1. **§3.1 洞察**：改数据的效果会在某个"状态页"上体现（订单提交页 → 订单列表页）。用一个**日常场景**说明，不用术语。
2. **§3.2 挑战**：C1（怎么在黑盒下找到状态页）、C2（怎么把应用导航到正确状态）
3. **§3.3 方案**：Technique I 对应 C1、Technique II 对应 C2

**C1 ↔ Technique I、C2 ↔ Technique II 的编号贯穿全文**（后面 §4.1、§4.2 都回指）。这给审稿人一种"结构闭合"的感觉。

**§3.1 的写法特别值得抄**：它先说"这在大多数情况下成立，因为应用通常会在专门页面上展示可被多渠道修改的数据"，然后举订单的例子。**先给一个常识性的理由，再举具体例子。** 不是上来就丢术语。

#### 4 Design（3 页）

- **4.1 IDDG**
  - 4.1.1 **形式化定义**：先定义导航图 `NE = {(n_prev, n_next) | Navigate(n_prev) = n_next}`，再定义 IDDE `IDDE = {(n_mod, n_status) | Dependency(n_mod) = n_status}`，再定义评分函数（Equation 1，三项加权）
  - 4.1.2 **构造**：页面探索 → token 插入 → 分层遍历（Level 1/2/3 优先级）
  - 4.1.3 **walk-through 例子**：Figure 4 用"订单"这一个例子，从页面截图 → IDDG 图 → 节点簇，三层展示
- **4.2 检测**：重放 → oracle 判定（INSERT/UPDATE/DELETE 三种不同判据）

**关键观察：有形式化定义（两个集合定义 + 一个公式）和算法伪代码（Algorithm 1/2）。**

我们的稿子目前**零形式化**。没有定义、没有公式、没有算法框。在顶会里这会被读成"这是个工程 hack，不是方法"。

#### 5 Evaluation（3.5 页，全文重心）

**5.1 Setup** 包含六件事，缺一不可：

| 要素 | 他们的做法 |
|---|---|
| Implementation | 4,116 行 Python；超参用 ground-truth 调（w1/w2/w3 = 0.4/0.3/0.3） |
| RQ 列表 | RQ1 有效性 / RQ2 对比 / RQ3 效率 / RQ4 组件有效性 |
| 数据集（双套） | **ground-truth set**（6 应用 / 44 已知漏洞）测 P/R；**testing set**（14 应用）找 0-day |
| 入选标准 | ≥100 stars、被前人评估过、多语言（Java/PHP/Go/TS） |
| 用户配置 | 2 victim + 1 attacker |
| 表 1 | 每个应用的 IDDE 数、漏洞数、CVE 数、stars、语言 |

**双数据集是整篇评估的命门。** 只有 testing set 无法算 precision/recall（没有 ground truth）；只有 ground-truth set 无法证明"能挖到新的"。两个都要。

**5.2 RQ1 有效性**：Table 2，MBAC 的 P=100.00% / R=83.33%，RBAC 的 P=83.33% / R=75.00%（ground truth set）；testing set 检出 33 个 0-day。
**5.3 RQ2 对比**：Table 3，对 EvoCrawl（NDSS'25）和 BurpSuite+Autorize。P 分别为 51.52% / 62.00%，他们 100%。
**5.4 RQ3 效率**：平均 1.1 小时/应用；自建 BACScan-Random 变体（关掉分层遍历）→ 2.3 小时，证明组件有用。
**5.5 RQ4 组件**：抽 10%（113 条）IDDE 人工核验，错误率 3.54%；再分析 IDDE 类型分布（INSERT 331 / UPDATE 452 / DELETE 352），发现 DELETE 只占 31.4% 却贡献 48.89% 的漏洞。

**5.6 案例**：两个 0-day，OpenEMR 和 XMall，各配一张 **完整 HTTP 请求/响应 + token 位置 + 行号**的图，并给出 CVE 编号（打码为 CVE-2024-46\*\*1）。

**这一节的四个手法：**
1. **误报和漏报都要做根因分析**，不能只报数字。"我们发现这些 FP 的主因是响应式 oracle 的固有缺陷"。
2. **自建弱化变体做消融**（BACScan-Random），证明每个组件都有用。
3. **人工抽检 10%** 来支撑自动构建的中间产物（IDDG）的可信度。
4. **案例图给到 HTTP 报文级别**，让审稿人能自己判断。

#### 6 Discussion（0.3 页）

只有两条局限：爬虫覆盖不全、GET 请求的性能取舍。加上一段 Ethics（三句话）。

**注意：他们承认的局限都是"工程可改进"的，不是"方法不成立"的。** 而且每条局限都配了数据（"GET 修改数据的情况只占 3.57%"）。

我们现在的 §5.4 写着"没有在真实应用里验证 path 可控"——这是**方法性局限**，在顶会里等于自曝死刑。必须补掉，不能只写在这里。

## 第四部分：两条重构路线

### 路线 A：Measurement 论文（测量向）

**标题**：*How Patches Fail to Propagate: Measuring Distribution-Form Drift in the npm Ecosystem*

**主张**：advisory 体系以包名为单位，代码以文件为单位，两者错配导致系统性修复盲区。

**需要的素材**：大规模测量（900 包样本 + 47 advisory + 全部 lodash 兄弟包），已有。

**可行性**：**高**，一周内可完成。
**风险**：顶会对纯 measurement 要求样本规模和统计严谨性（需要抽样方法论证、置信区间、可能的纵向数据）。我们的 900 包样本是"关键词采样"，在方法论上会被挑。

### 路线 B：Attack/Tool 论文（工具向，**接近 BACScan 的形态**）

**标题**：*Clean Prototype, Dirty Read: Detecting Prototype-Chain Traversal in npm Applications*

**主张**：读侧穿越是一个未被建模的攻击面；现有检测（污染检测、SCA）结构性看不见它；我们造一个检测器，在真实应用里找到 N 个可达点、M 个 0-day。

**核心一击**（对应机关 3）：
> Existing detectors are predicated on a flawed assumption: that a prototype-chain vulnerability must leave a trace in `Object.prototype`.

**需要的素材**：
- 检测器：`scan.js` 已有雏形（AST + 绑定追踪），要补"跨文件数据流 + 输入源识别"
- **ground truth**：用 47 条历史 CVE 的修复 commit 反推（36 条有 commit 链接）→ 构造"应当检出"的标注集
- **testing set**：20 个真实 Node 应用
- **baseline**：npm audit / OSV-Scanner / CodeQL 自定义查询 / Semgrep
- **0-day**：在 testing set 里找可达且可执行的路径

**可行性**：中，2-4 周。
**风险**：0-day 的产量不可控。但 BACScan 的 54 个 0-day 里，很多是"同类问题的多处实例"，不是 54 个独立发现。

### 推荐：B，但先做 B 的"可行性探针"

理由：A 的天花板是 workshop（我们的 900 包样本撑不起顶会的测量标准），B 才有顶会形态。而且 B 直接服务于你最初的目标——**挖真实漏洞**。

**探针**（3 天内可完成，决定要不要投入 B）：
1. 拿 10 个真实 Node 应用（Ghost / Node-RED / Parse Server / Strapi / Directus / Medusa / Keystone / Payload / Apostrophe / Sails）
2. 用 `scan.js` 扫一遍，数 tainted 调用点
3. 人工核查其中 20 处：**path 是否真的来自外部输入**
4. 判定：
   - 若 ≥3 处可追到 `req.*` / 用户配置 → **B 成立，全力投入**
   - 若 0-2 处 → B 不成立，退 A，或改成"库层 + 生态测量"的混合形态

### 必须有的形式化（现在完全没有）

至少三件：

1. **path 语义定义**
   ```
   ⟦·⟧ : Path × Object ⇀ Value
   ⟦ε⟧(o) = o
   ⟦k·p⟧(o) = ⟦p⟧(o[k])   当 o ≠ null
   ```
   然后定义 traversal：`∃p. ⟦p⟧({}) ∈ Function`

2. **检测谓词**（把"非字面量"严格化）
   ```
   对调用点 c: f(o, p)，若 p ∉ Literal* 且 p 受源 s 支配，则 c 可疑
   ```
   配一个 taint 格：`⊥ ⊑ {safe} ⊑ {tainted}`，把我们的 `unknown/SHAPE` 正式化成一个第三值（**这正好是我们的四值判定的理论包装**）。

3. **分发形态等价关系**
   ```
   forms(f) = {m | m 是 f 的可解析分发形态}
   drift(f) = |{m ∈ forms(f) : code(m) ≠ code(main)}|
   ```
   把"断层"变成一个可计算的量。

### 评估设计（最关键，决定能不能中）

**双数据集**（照抄 BACScan 的思路，但素材换成我们的）：

| 数据集 | 构成 | 用途 |
|---|---|---|
| **Ground-truth set** | 47 条历史 CVE 中，36 条有修复 commit → 反向构造"应当检出的代码点"；再加 10 个已知安全实现作负样本 | 算 P/R |
| **Testing set** | 20 个真实 Node 应用（≥3k stars，覆盖 Express/Koa/Nest 三种框架） | 找 0-day |

**四个 RQ**（照抄结构）：

- **RQ1 有效性**：ground-truth 上的 P/R；testing set 上的发现数
- **RQ2 对比**：vs npm audit / OSV-Scanner / CodeQL 查询 / Semgrep 规则。**预期我们赢在"别人根本不检这一类"**，这比赢在数字上更好讲
- **RQ3 效率**：每应用耗时；对比纯静态 vs 我们
- **RQ4 消融**：四值判定 vs 二值判定（把 SHAPE 当 MISS）→ 假阴性率差多少。**这是我们的独有卖点，一定要单独一个 RQ**

**案例**：至少 2 个真实应用，给到 HTTP 请求/配置 + 调用栈 + 实际执行结果（`process.version` 或无害命令）。

## 第六部分：写作风格规则（从 BACScan 提炼，可直接执行）

### 句式模板

| 场景 | 模板 | BACScan 原句 |
|---|---|---|
| 转折 | `Although X is a well-explored topic, <反面趋势> highlights the long-lasting lack of <能力>.` | "Although BAC vulnerability detection is a well-explored research topic, the increasing severity..." |
| 攻击假设 | `X is predicated on a flawed assumption: <假设内容>.` | "the response-based oracle is based on a flawed assumption" |
| 定位自己 | `Unlike existing <类别> that <局限>, we <差异>.` | "Unlike existing response similarity-based oracles that check only unauthorized read accesses, BACScan introduces..." |
| 承认前人 | `While the high-level idea is reasonable, these approaches still present notable limitations due to <具体>.` | 2.2 节 |
| 引出挑战 | `This may appear straightforward. However, <难点> presents significant difficulties.` | 3.2 开头 |

### 禁用词（我们现在稿子里全是）

| 禁用 | 原因 | 换成 |
|---|---|---|
| "we believe" / "we think" | 顶会不认主观 | 给数据或删掉 |
| "very" / "extremely" / "significantly"（无数据时） | 空强调 | 给百分比 |
| "novel"（自己说自己新） | 自吹 | 说差异，让审稿人判断 |
| "obviously" / "clearly" | 读者可能不觉得 | 删 |
| "in this paper, we..." 开头段 | 太弱 | 先从问题/数据开始 |

### 段落规则

1. **每段第一句必须是论点**，不是铺垫。
2. **数字必须有出处**（表号/节号/URL），不能是"经验估计"。
3. **每个 claim 后面跟证据**（表/图/节号）。
4. **每节开头一句话交代本节结构**（"In this section, we first ... then ... finally ..."）。
5. **术语第一次出现给定义**，之后严格一致（我们现在 traversal/pollution 混用过）。
