# lodash 修复完整性审计：一把装了 8 年的锁，只装在一扇门上

日期：2026-11-02
对象：lodash 4.18.1（npm dist-tags.latest，2026-04-01）
方法：修复不变量传播检查（从 patch 提取「它保护了什么」，再查「做同一件事的其他路径有没有被保护」）

---

## 一、核心发现（一句话）

lodash 内部**早就有正确的防护实现** `safeGet()`，注释明确写着「除非 key 是 `__proto__` 或 `constructor`」，
但它只被 `baseMerge` / `baseMergeDeep` 调用（3 处），
**所有读型穿越（`baseGet` / `parent`）和调用型穿越（`baseInvoke`）一次都没用过它。**

这不是「不知道怎么防」，是「防了但没防到地方」。

---

## 二、全库只有 4 处原型污染 guard

用 `grep "Prevent prototype pollution"` + 键名比较两种方式交叉核对，4.18.1 全库仅 4 处：

| 行号 | 所属函数 | 判据 | 行为 |
|---|---|---|---|
| 4040 | `baseSet` | `key === '__proto__' \|\| key === 'constructor' \|\| key === 'prototype'` | `return object`（静默丢弃） |
| 4393 | `baseUnset` | `key === '__proto__' && !hasOwnProperty.call(object,'__proto__')` | `return false` |
| 4399 | `baseUnset` | `(key === 'constructor' \|\| key === 'prototype') && index < length - 1` | 拦截（仅非末位） |
| **6705** | **`safeGet`** | `key === 'constructor' && typeof object[key] === 'function'` / `key == '__proto__'` | `return undefined` |

`safeGet` 的原始注释：

```js
/**
 * Gets the value at `key`, unless `key` is "__proto__" or "constructor".
 */
function safeGet(object, key) {
  if (key === 'constructor' && typeof object[key] === 'function') {
    return;
  }
  if (key == '__proto__') {
    return;
  }
  return object[key];
}
```

**这个判据是对的**：`__proto__` 无条件挡；`constructor` 仅在「它确实是函数」时挡
（这样不会误伤业务里自有 `constructor` 字段）。它在 4.17.20 第 6631 行就已经存在。

### 但它只被两个函数用

| 函数 | safeGet 调用次数 |
|---|---|
| `baseMerge` | 1（line 3654） |
| `baseMergeDeep` | 2（line 3681、3682） |
| **`baseGet`** | **0** |
| **`parent`** | **0** |
| **`baseInvoke`** | **0** |
| **`result`** | **0** |

而 `baseGet` 就是读型的唯一通道，`parent` 是 `baseInvoke` 的必经点。
**锁在 `merge` 这道门上，`get`/`invoke` 那道门一直开着。**

## 三、攻击面实测（4.18.1 原版，全部可穿）

判据统一为「取到 Function」或「执行出唯一 marker」，不看返回值形态（否则会把语法错误误判成拦截）。

| 入口 | 类型 | 4.18.1 | 备注 |
|---|---|---|---|
| `_.get` | 读 | **穿** | 数组/字符串 path 均可 |
| `_.at` | 读 | **穿** | 本轮新增，此前未测 |
| `_.invoke` | 调用 | **穿 → RCE** | |
| `_.invokeMap` | 调用 | **穿 → RCE** | |
| `_.method` | 调用 | **穿 → RCE** | |
| `_.methodOf` | 调用 | **穿 → RCE** | 正确签名 `methodOf(obj, ...args)(path)` |
| `_.chain().invokeMap` | 调用 | **穿 → RCE** | 惰性链同样 |
| `_.invokeMap` + `.map(f=>f())` | 调用 | **穿 → RCE** | 批量执行形态 |

`_.result` 不在此列 —— 见第六节。

## 四、最小修复与验证（这是给厂商的核心交付物）

只改 `baseGet` 一处，加 2 行：

```js
while (object != null && index < length) {
  var key = toKey(path[index++]);
  if (key === '__proto__' || (key === 'constructor' && typeof object[key] === 'function')) {
    return undefined;
  }
  object = object[key];
}
```

判据与 `safeGet` 完全一致（复用官方已有语义，不发明新规则）。

### 结果

| 指标 | 结果 |
|---|---|
| 攻击入口封堵 | **8 / 8** |
| 功能回归（17 项） | **17 / 17 一致** |

回归覆盖：`get` 嵌套 / 数组索引 / 默认值、`set` 嵌套 / 危险键、`unset`、`merge` / 危险键、
`invoke` / `invokeMap` / `method` / `at` 正常用法、`pick` / `omit` / `has` / `template` / `map` / `filter`。

### 为什么一处改动能覆盖 8 个入口

因为 `invoke` / `invokeMap` / `method` / `methodOf` / `at` 全部经过 `baseGet`（或经 `parent` → `baseGet`）。
**这正是「应该有统一穿越守卫」的直接证据**：现有代码在 8 个入口上散落着 8 份穿越逻辑，
其中 6 份共用 `baseGet`，2 份（`get` / `at`）直接用它 —— 修一处，全收敛。

## 五、修复完整性矩阵（历史 CVE → 修复点 → 同语义未覆盖）

| CVE / GHSA | 修复落点 | 修的是 | 同语义路径是否被覆盖 |
|---|---|---|---|
| CVE-2018-3721 | 引入 `safeGet` | merge 写入 | ❌ 读型从未覆盖 |
| CVE-2018-16487 | —（修复不完整的回归） | merge | ❌ 同上（二手源，未逐版本验证） |
| CVE-2019-10744 | `defaultsDeep` → merge 家族 | 写入 | ❌ 读型未覆盖 |
| CVE-2020-8203 | `zipObjectDeep` | 写入 | ❌ 读型未覆盖 |
| CVE-2021-23337 | `template` variable | 代码生成 | ⚠ 见第七节 |
| CVE-2026-2950 | `baseUnset`（2 处 guard） | 删除 + 非末位穿越 | ❌ `baseGet`/`baseInvoke` 未覆盖 |
| **本次发现** | 无 | — | `invoke` 家族 + `get`/`at` |

**模式很清楚**：每一次修复都精准落在「出事的那一个函数」上，从没有一次落到了「穿越」这个抽象层。

## 六、`_.result` 为什么不能 RCE（精确解释，避免误报）

`result` 也是无 guard 的调用型 sink，但它拿不到 RCE：

```js
while (++index < length) {
  var value = object == null ? undefined : object[toKey(path[index])];
  if (value === undefined) { index = length; value = defaultValue; }
  object = isFunction(value) ? value.call(object) : value;   // 边走边调
}
```

它**每走一跳就调用一次**。走 `['__proto__','constructor','constructor']` 时：
- 第 2 跳拿到 `Object`，`Object.call(Object.prototype)` 返回 `{}`
- 第三跳的 `object` 已经是 `{}` 而不是 `Object`，`({}).constructor` 又是 `Object`，再调一次
- 最终返回 `{}`，永远到不了 `Function`

所以 `_.result` 只能调零参函数（`_.result({}, ['__proto__','__defineGetter__'])` 会抛
`TypeError: ... Expecting function` —— 这条报错本身就是「确实调到了原型方法」的证据，但不是 RCE）。

**结论：`result` 记为「确认可调原型方法」，不报 RCE 级。** 这个区分不做，就会被审稿人或维护者一击打回。

## 七、`_.template` 的修复：脆弱，但未找到绕过（诚实记录）

4.18.0 同时修了 template 注入，用的是字符黑名单：

```js
var reForbiddenIdentifierChars = /[()=,{}\[\]\/\s]/;
```

实测 24 个 `variable` 取值 + 6 个 `imports` key：

| 输入 | 结果 | 拦截者 |
|---|---|---|
| `a b`（空格）、`a　b`（全角空格） | REJECT | **lodash 黑名单** |
| `a){}` (imports) | REJECT | **lodash 黑名单** |
| `a;b`、`a.b`、`a-b`、`a+b`、`a<b`、`a:b`、引号、反斜杠 | REJECT | **JS 语法错误**（不是黑名单） |
| `arguments`、`eval`、`变量` | **ACCEPT** | 合法标识符，无害 |

**关键观察**：大部分「拒绝」来自「生成的代码恰好语法不合法」，而不是显式校验。
黑名单只挡了 10 个字符，剩下 20 多个运算符字符全靠语法兜底。

这是**脆弱修复**：一旦 lodash 改变 template 的代码生成位置（比如把 variable 拼到非参数位），
黑名单立即失效。但就当前实现而言，**我没找到可利用的绕过** ——
要注入必须在参数列表里插表达式，而 `(` `,` `=` 全在黑名单里。

按四值判定记 **ineffective（未打通）**，不是 fixed。

## 八、边界与不确定

1. **只测 Node 22 + 独立引入**，未测浏览器打包、`lodash/fp`（fp 的 `convert` 重排参数，5 种形态均未打通，记 ineffective）。
2. **最小修复会带来行为变化**：`_.get(obj, 'constructor')` 从「返回 Object」变成 `undefined`。
   这是可接受的（谁会依赖读 `constructor`？），但属于 breaking change，厂商需要权衡。
3. **`safeGet` 的 `typeof === 'function'` 条件**看起来有绕过空间（让 `constructor` 不是函数即可放行），
   但实测走不通：要让 `constructor` 指向非函数且其 `prototype` 仍是 `Object.prototype` 不成立。
   **记「已验证不可绕过」，不是「未检查」。**
4. 历史 CVE 的修复落点，CVE-2018-16487 一条来自二手源（Sonatype 分析），未逐版本复现。

## 九、这轮方法论的产出（可迁移部分）

**「修复不变量传播检查」的可执行定义**：

1. 从 patch diff 里找出新增的判据（guard），提取它的**语义**（挡什么键、在什么位置挡、挡了之后做什么）
2. 枚举做**同一件事**的所有函数（这里是「沿 path 穿越对象图」）
3. 对每个函数标注 guard 覆盖情况 → 得到矩阵
4. 未覆盖的格子逐个实测，用**可执行标记**判定，不用返回值形态判定
5. 给出最小修复，并跑「攻击全封堵 + 功能全回归」双向验证

第 5 步是这套方法区别于「报一个洞就走」的地方：**它证明修复成本极低，从而把讨论从「这是不是漏洞」拉到「你为什么不修」。**
