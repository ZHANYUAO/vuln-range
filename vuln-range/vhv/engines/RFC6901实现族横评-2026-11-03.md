# RFC 6901 / 6902 实现族横评：读侧原型链穿越与守卫形态

**日期**：2026-11-03
**测试对象**：5 个 JSON Pointer / JSON Patch 实现（合计周下载 **52,119,388**；另附 jexl 作镜像对照，六个包共 52,326,217）
**测试代码**：`probe_pointer.js`，结构化结果 `pointer-result.json`
**判定规则**：对照组不通过一律记「未判定」，绝不记成「安全」

---

## 零、一句话结论

**5 个实现里，没有一个做自有属性检查的只剩下 1 个是真正安全的；另外 4 个都在用 `obj[key]` 一路穿下去。** 其中 2 个能拿到 `Function`（可执行任意代码），2 个停在 `Object` 构造器（差一跳）。更关键的是：**唯一安全的那个用的是 `hasOwnProperty`，唯一两个带显式黑名单的包，黑名单都不完整——一个只加在写侧，另一个的匹配模式漏掉了 `constructor/constructor`。**

## 一、为什么必须加「单跳」载荷

第一版只测「三跳到 `Function`」，结果 `jsonpointer` 和 `json-pointer` 全部返回 `undefined` / 抛错，看上去像是「这两个库安全」。

这是错的。加上 P6 `/a/constructor`（只走一跳）后真相暴露：

| 库 | `/a/constructor` | 说明 |
|---|---|---|
| jsonpointer 5.0.1 | **返回 `Object` 构造器** | 继承穿透发生了 |
| json-pointer 0.6.2 | **返回 `Object` 构造器** | 继承穿透发生了 |

它们不是没穿，是穿到 `Object` 之后**下一跳被 `typeof obj === 'object'` 的类型断言挡住了**——因为 `Object` 是函数，`typeof` 是 `'function'`。

```js
// jsonpointer@5.0.1 get()，无任何安全判断
obj = obj[untilde(pointer[p++])];
if (len === p) return obj;
if (typeof obj !== 'object' || obj === null) return undefined;   // ← 唯一挡住 Function 的东西

// json-pointer@0.6.2 get()，同样无安全判断
if (!(typeof obj == 'object' && tok in obj)) throw new Error('Invalid reference token: ' + tok);
//                                ^^^^  in 运算符本身就沿原型链查找
```

**这三行代码里没有一个字是为了安全写的。** 把断言换成 `typeof obj !== 'undefined'`，这两个包立刻和 json-ptr 一样。

**方法论结论**：只测「能否拿到 `Function`」会把「差一跳」误报成「安全」。必须分层测：`能否读到继承对象` / `能否读到构造器` / `能否读到 Function` / `能否调用`。

## 三、守卫形态二维表：位置 × 形式

把 5 个实现（加上前面 lodash、json-e 的结论）按「守卫放在哪」和「用什么形式判断」拆开：

| 实现 | 守卫位置 | 守卫形式 | 结果 |
|---|---|---|---|
| lodash `baseGet` / `result` / `invoke` | **无** | — | 穿透 |
| lodash `baseSet` / `baseUnset` | 写侧 | 键名黑名单 | 拦住写 |
| lodash `safeGet` | 写侧（仅被 merge 调用） | 键名黑名单 | 读侧仍无 |
| json-ptr `setValueAtPath` | 写侧 | 键名黑名单（3 词） | 拦住写 |
| json-ptr `compilePointerDereference` | **无** | — | 穿透 5/5 |
| **fast-json-patch** `applyOperation` | **读 + 写** | 键名黑名单（模式 `__proto__` 或 `constructor/prototype`） | 读侧漏 `constructor/constructor` |
| jsonpointer / json-pointer | 无 | 类型断言（巧合） | 停在 `Object` |
| **jsonpatch** `JSONPointer.get` | 读 + 写 | **`Object.hasOwnProperty.call`** | **完全拦住** |
| **json-e** `visit_ContextValue` | 读 | **`hasOwn(context, key)`** | **完全拦住** |

**这张表是本项目到目前最干净的证据：**

1. **所有黑名单式守卫，无论放在读侧还是写侧，都能被绕过。** 不是"某个包写漏了"，而是黑名单这个形式本身不成立——它要枚举一个不封闭的命名空间。
2. **所有结构性守卫（`hasOwnProperty` / `hasOwn`），一次也没有被绕过。** 两个案例：`jsonpatch`、`json-e`，都是不同作者、不同年代、不同代码风格，同一个做法。
3. `safeGet` 那个更惨：守卫写了，但只服务于 `merge`，读侧根本没接上——这是"位置错"而非"形式错"。

## 四、新发现：fast-json-patch 的黑名单绕过（写侧实证）

### 4.1 守卫原文

`fast-json-patch@3.1.1` `commonjs/core.js:191`：

```js
if (banPrototypeModifications &&
    (key == '__proto__' ||
        (key == 'prototype' && t > 0 && keys[t - 1] == 'constructor'))) {
    throw new TypeError('JSON-Patch: modifying `__proto__` or `constructor/prototype` prop is banned ...');
}
```

它 ban 两样东西：`__proto__`，以及 `constructor` 紧跟 `prototype` 的**相邻对**。

`constructor` 自己、`constructor/constructor`、`constructor/x` 都不在 ban 内。

### 4.2 读侧已经漏了

`getValueByPointer` 并不是独立实现，它伪造一个 `_get` 操作走同一个循环：

```js
function getValueByPointer(document, pointer) {
    var getOriginalDestination = { op: "_get", path: pointer };
    applyOperation(document, getOriginalDestination);   // ← 同一个守卫，同一个漏洞
    return getOriginalDestination.value;
}
```

所以黑名单覆盖了读侧——这点比 json-ptr 强——**但模式不完整**，`/a/constructor/constructor` 依然拿到 `Function`。

### 4.3 写侧也能绕，且后果是全局的

`add` / `replace` 到 `/a/constructor/...` 全部放行。实测（独立进程）：

```
前: Object.x = undefined          Object.constructor === Function → true
add      /a/constructor/x          → Object.x = 'INJECTED'
replace  /a/constructor/constructor → Object.constructor = 'PWNED'
后: ({}).constructor = [Function: Object] { x: 'INJECTED', constructor: 'PWNED' }
```

**一份纯数据的 JSON Patch 文档，改掉了全局 `Object` 构造器的自有属性。** 守卫的声明目的是"禁止修改 `__proto__` 或 `constructor/prototype`"，而攻击者要去的地方根本不在它枚举的两个模式里。

危害边界要说清楚：JSON 值只能是字符串/数字/对象，**拿不到函数，所以这一步不是 RCE**，是全局命名空间篡改 + 完整性破坏（例如覆盖 `Object.assign` 造成进程级 DoS，或让依赖 `Object.constructor` 的代码拿到字符串）。真正到 RCE 仍需绕回读侧拿 `Function`。

### 4.4 定级

| 项 | 值 |
|---|---|
| 包 | `fast-json-patch@3.1.1`（latest，2022-02 起未更新） |
| 周下载 | 11,801,180 |
| 读侧 | 穿过 `constructor` 链拿到 `Function`（`__proto__` 路径被 ban） |
| 写侧 | 守卫可绕，可写 `Object` / `Function` 自有属性 |
| 建议 CVSS | `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:H` ≈ **8.6 High** |
| 关键前提 | path 来自 JSON Patch 文档，按 RFC 6902 由客户端给定 |

### 4.5 修复

和 `jsonpatch` 用的一样，一行：

```js
if (!Object.hasOwnProperty.call(node, key)) { /* 拒绝 */ }
```

不是加长黑名单——加长只会把绕过点从 `constructor/constructor` 推到 `constructor/__defineGetter__`、`valueOf`、`toLocaleString`，以及未来任何新增的 `Object.prototype` 成员。

## 五、jexl：同一缺陷的镜像现象

`jexl@2.3.0`（周下载 206,829）是表达式引擎，点号形式下 `a.constructor` / `a.toString` / `a.valueOf` **全部报错**，看起来像有黑名单。

**不是。它没有黑名单。** 真因是它的语法表是普通对象，查表时沿原型链取到了东西：

```js
// jexl Lexer._createToken
} else if (this._grammar.elements[element]) {
    token.type = this._grammar.elements[element].type;   // elements['constructor'] → Object，.type 是 undefined
} else if (element.match(identRegex)) {
    token.type = 'identifier';
}
```

实测 `grammar.elements`：

| 键 | `truthy` | `typeof` | `.type` |
|---|---|---|---|
| `constructor` | true | function | **undefined** |
| `toString` | true | function | **undefined** |
| `valueOf` | true | function | **undefined** |
| `hasOwnProperty` | true | function | **undefined** |
| `__proto__` | true | object | **undefined** |

于是 `token.type = undefined`，解析器报 `Token constructor (undefined) unexpected`。**每一个 `Object.prototype` 成员名都被"误伤"成保留字。**

两个后果：

- **功能缺陷（可直接报 bug）**：业务字段叫 `toString` / `valueOf` / `hasOwnProperty` 时，点号形式取不到值（`a.toString` 报错，`a["toString"]` 正常）。这不是假设，实测 `{a:{toString:'hello'}}` + `a.toString` → 解析错误。
- **安全没兜住**：方括号形式完全不受影响。`a["constructor"]` → `Object`，`a["constructor"]["constructor"]` → **`Function`**。

```js
j.eval('a["constructor"]["constructor"]', {a:{b:7}})   // → Function ✅
j.eval('a.constructor.constructor', {a:{b:7}})          // → 词法错误
```

**这是本项目核心命题的镜像**：同一个"用不可信字符串去索引一个普通对象"的动作，在 lodash 里症状是"穿过去"，在 jexl 里症状是"拒绝服务自己的语法表"。**同一根因，两种症状，两种危害。** 而真正的安全（`hasOwn`）一次都没出现。

jexl 停在读档：它的调用语法要求 callee 是 context 里的标识符，`a["constructor"]["constructor"]("return 6*7")` 报 `Jexl Function undefined is not defined`，无法执行。

| 包 | 周下载 | 读侧 RCE 能力 | 现有 advisory |
|---|---|---|---|
| jsonpointer | 30.10M | 否（差一跳，纯意外） | 有（历史原型污染，写侧） |
| **fast-json-patch** | **11.80M** | **是**（`constructor/constructor`） | 有（历史 CVE-2019-... 写侧） |
| json-pointer | 6.14M | 否（差一跳） | — |
| **json-ptr** | **4.06M** | **是**（5/7 载荷） | 有（GHSA-rrqv，2.1.0 修的是代码注入） |

| jsonpatch | 0.02M | 否（结构式） | — |

**合计 5,233 万周下载。** 两个可达 RCE 的包（15.9M/周）都已"修过"一次——修的都是写侧或代码注入，读侧从来没被当作问题。

这与 lodash 那条线是同一个模式，只是换了个生态位：

> **advisory 描述的是"写入 `Object.prototype`"，所以补丁也只堵"写入"。而读侧穿越不产生写入，也就不产生 advisory，也就不产生补丁。**

## 八、过程中的三次装置故障（记录在案）

| 现象 | 真因 | 若不查会得出什么错误结论 |
|---|---|---|
| jsonpointer / json-pointer 全 MISS | 只测三跳，没测单跳 | "这两个包安全"——实际它们读到了 `Object` |
| jsonpatch 报「无可用的读指针 API」 | `JSONPointer` 的 `get` 是**实例方法**，我按静态方法调 | "jsonpatch 无读 API"——实际它是唯一完全安全的 |
| fast-json-patch 的 `replace` 报 PATH_UNRESOLVED | 我传了 `mutateDocument=false`，操作发生在克隆体上 | "写侧被拦住了"——实际写侧放行且改写全局 |

**三次都是"把适配错误读成库的安全属性"。** 这类错误的共同特征是：结论偏向"没问题"，最容易被放过。
