# 引擎扫描报告：json-ptr 读侧穿透，以及「守卫只加在写侧」的第四例

> 日期：2026-11-02　环境：Node v22.22.2 / Windows
> 生成器：`engines/probe_engines.js`、`engines/poc_engines.js`
> 证据：`engines/engines-result.json`、`engines/poc-result.json`

---

## 一、为什么换目标

上一轮实测 8 个真实 Web 应用（Ghost / Strapi / Directus / n8n / NocoBase / Apostrophe / Parse Server），6457 文件，HTTP 级可达 **2 处，成立 0 处**。

那不是「漏洞不严重」，是**测量场景选错了**。我测的是「应用有没有恰好把用户输入当 path」，而真正的问题是：

> **哪些组件的存在前提，就是「让不可信输入指定访问路径」？**

答案是一类库：JSON Pointer、JSONPath、规则引擎、表达式求值器。它们不是"可能暴露 path"，是**职责本身就是消费 path**。

---

## 二、方法：先证明装置没坏，再下结论

扫描 9 个引擎，每个都先跑正常取值对照（`a.b → 7`）。**对照失败一律记 NA，不记 MISS。**

这一条在本轮救了两次：

| 误判风险 | 真因 | 后果（若不查） |
|---|---|---|
| `jsonata` 对照返回 `{}` | `evaluate` 是**异步**，返回 Promise | 差点记成"安全" |
| `json-e` 全部报错 | `__dirname` 在 `node -e` 下是 `.` | 差点记成"库不可用" |
| `json-ptr` $ref 场景失败 | API 名写错（`fromPtr` 不存在） | 差点漏掉一个场景 |

## 四、json-ptr 3.1.1：写侧拦了，读侧没拦

这是本轮最硬的发现。同一个库、同一个 `__proto__` 段，两条路径两种结果：

```
[PASS] A1:setGuard    写侧 /__proto__ 被拦截 → "Attempted prototype pollution disallowed."
[HIT ] A2:readBypass  读侧同一段未被拦截    → 取到 Function 本体
```

### 4.1 源码级证据

`setValueAtPath`（写侧，L190 起）逐个段落检查：

```js
if (
  // Reconsider this strategy. It disallows legitimate structures on
  // non-objects, or more precisely, on objects not derived from a class...
  step === '__proto__' || step === 'constructor' || step === 'prototype') {
  throw new Error('Attempted prototype pollution disallowed.');
}
```

`compilePointerDereference`（读侧，L170）—— **零检查**，而且把路径段直接拼进代码：

```js
body = path.reduce((body, _, i) =>
  body + "\n && it !== null && typeof((it = it['" +
  escape(path[i]) + "'])) !== 'undefined'", "if (typeof(it) !== 'undefined'");
return new Function('it', body);   // ← 路径编译成 JS 源码
```

两个后果：

1. **`new Function` 让所有静态检查失效** —— 路径不是"被解析的数据"，而是"被编译的代码"，SAST 看不见。
2. **转义只防注入，不防访问** —— 它正确转义了 `\` 和 `'`，所以 2.1.0 那个代码注入 CVE 确实修好了。但 `__proto__` 是**合法的 RFC 6901 指针段**，不需要任何注入技巧就能穿过继承链。

### 4.2 全链路可达

| 阶段 | 结果 |
|---|---|
| 取 Function | `/__proto__/constructor/constructor` |
| 执行表达式 | `Function('return 6*7')()` → `42` |
| 读任意文件 | `fs.readFileSync` 读到 3700 字节 |
| 起子进程 | `execSync('echo PTR_RCE_OK')` → 成功 |

### 4.3 三个真实场景都能触发

| 场景 | 攻击路径 | 实测 |
|---|---|---|
| **RFC 6902 JSON Patch** | 客户端请求体 `{"op":"test","path":"/__proto__/constructor/constructor"}`，`test` 只读不写，**不会碰 set 守卫** | HIT，客户端拿到 `matched=true` |
| 通用取值 API | `JsonPointer.get(cfg, req.query.p)` 结果回显 | HIT，返回 `type=function` |
| JSON Schema `$ref` | `new JsonReference('/__proto__/...').resolve(obj)` | HIT，返回 function |

**JSON Patch 这一条最关键**：RFC 6902 的 `path` 字段按规范就来自客户端，不是"用户碰巧能控"，而是**协议要求它可控**。

### 4.4 它有一个更尖锐的地方

OSV 里躺着的 GHSA-rrqv-vjrw-hrcr，标题就叫 *Arbitrary Code Execution in json-ptr*，原文写着：

> "If your code sends un-sanitized user input to json-ptr's **.get() method**, your project is vulnerable to this injection-style vulnerability."

**同一个方法、同一个入口，第二次被攻破。** 2.1.0 的修复把问题定性为"代码注入"，于是修法是转义字符；而真正缺的那件事——**`get` 没有访问控制**——从来没被修过。

## 五、json-logic-js 2.0.5：`var` 操作符是 `baseGet` 的翻版

```js
"var": function(a, b) {
  var sub_props = String(a).split(".");
  for (var i = 0; i < sub_props.length; i++) {
    data = data[sub_props[i]];      // ← 裸下标，不区分 own / inherited
  }
  return data;
}
```

和 lodash 的 `baseGet` 结构完全一致：同一个 `while`，同一个裸下标，同一个零守卫。但**它是独立实现，不依赖 lodash**。

结论：这不是 lodash 的 bug，是**「按点分路径取属性」这种写法的通病**。

它停在一档，因为历史 CVE（GHSA-m9hw-7xfv-wqg7）的修复方式是**直接把 `method` 操作符从库里删掉**：

```
[HIT ] B1:varBypass   var 操作符穿越到 Function
[MISS] B2:methodOld   历史 payload → "Unrecognized operation method"
[MISS] B3:combo1      var + method 组合 → 同上（操作符已不存在）
```

所以它只能**读到** Function，不能在单条规则内调用。危害降一档，但性质同样严重：

> json-logic 的市场定位是「**eval 的安全替代品**」——用数据描述规则，避免执行代码。
> 而它会把 `Function` 构造器原样递给调用方。安全承诺在"取属性"这一步就已经破了。

## 六、核心对照：四种实现，四种守卫策略

这是本轮最值得写进论文的一张表。**同一个语义（按路径取属性），四个独立实现，四种命运**：

| 实现 | 守卫方式 | 位置 | 结果 |
|---|---|---|---|
| lodash `baseGet` | 无 | — | 穿透 |
| json-ptr `compilePointerDereference` | 无 | — | 穿透 |
| json-logic `var` | 无 | — | 穿透 |
| json-ptr `setValueAtPath` | 黑名单（3 个词） | 只写侧 | 拦住 |
| lodash `safeGet` | 黑名单 | 只被 merge 调用 | 写侧拦住，读侧无 |
| **json-e `visit_ContextValue`** | **`hasOwn`** | **每次取值** | **拦住，且不需要黑名单** |

```js
// json-e 的做法（interpreter.js:216）
visit_ContextValue(node) {
  if (hasOwn(this.context, node.token.value)) {   // ← 结构式，从根上关掉继承
    return this.context[node.token.value];
  }
  throw new InterpreterError(`unknown context value ${node.token.value}`);
}
```

**黑名单是"列举已知攻击词"，`hasOwn` 是"改变访问语义"。** 前者需要预知 `__proto__`、`constructor`、`prototype`、`__defineGetter__`……以及未来所有新增的；后者一次到位。

本项目的全部证据可以归结为一句话：

> **所有被修过的地方，用的都是黑名单；所有用 `hasOwn` 的地方，都没出过问题。**

| 目标 | CVSS | 依据 |
|---|---|---|
| **json-ptr 3.1.1** | **9.1 Critical**　`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` | AC 可给 L：JSON Patch 的 path 按协议就是客户端给的，不需要"碰巧可控" |

与 lodash 那批的区别：lodash 停在"库里有缺陷"（应用 0/8 可达），**json-ptr 已经到"应用有漏洞"**——因为它的输入通道由协议规定必须开放。

## 八、修复建议

**给 json-ptr**（最小改动，插在 `compilePointerDereference` 的 `reduce` 里）：

```js
body = path.reduce((body, _, i) => {
  const seg = path[i] + '';
  if (seg === '__proto__' || seg === 'constructor' || seg === 'prototype') {
    // 与写侧保持一致的拒绝语义，而不是静默返回 undefined
    return body + "\n && (() => { throw new Error('Attempted prototype pollution disallowed.'); })()";
  }
  ...
```

更彻底的做法是照 json-e：**不要用 `new Function` 编译路径**，改成逐段 `hasOwn` 循环。代价是性能，收益是这条路以后再也不会被绕。

**给 json-logic-js**：`var` 的每段取值换成 `hasOwn(data, key) ? data[key] : not_found`。

**给下游使用者**（临时缓解）：在调用前加 `if (/__proto__|constructor|prototype/.test(JSON.stringify(path))) throw`。注意这条对数组 path 要单独处理（`typeof p === 'string'` 会被绕过，这是本项目早前实测过的）。

## 九、局限

1. **jexl 未测**（缺 `@babel/runtime`），不排除同类问题。
2. json-ptr 的 `set` 守卫**确实有效**，本轮没有找到 3.1.1 的写侧绕过。
3. `compilePointerDereference` 的转义是对的，**我没有找到代码注入**；本报告的结论是"访问控制缺失"，不是"注入"。
4. json-logic 停在一档，未找到单规则内调用 Function 的组合（`method` 已被移除；`map`/`filter`/`reduce` 只把数据当参数，不调用）。
