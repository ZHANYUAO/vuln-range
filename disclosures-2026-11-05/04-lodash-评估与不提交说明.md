# lodash 系列：为什么**不**按漏洞提交（实事求是评估）

> 对应 11-02 的 `P0-披露报告-分发形态断层-lodash-2026-11-02.md`。
> 那份报告的技术事实全部成立，但「是否构成可提交漏洞」这个结论，复核后**不成立**。

---

## 一、原始主张

`_.get(obj, path)` / `_.get(obj, ['__proto__','constructor','constructor'])` 能读到 `Function` 构造器，
且 `lodash.get@4.4.2`（22,320,171 次/周）与 `lodash.invoke@4.5.2` **0 条 advisory**，
兄弟包自 2016-08-13 起集体冻结。

## 二、为什么它不是可提交漏洞

| 判据 | 事实 | 结论 |
|---|---|---|
| **是否违背了库的承诺** | `_.get` 的文档语义就是「按 path 取属性」；它从未承诺阻止原型链访问，也没有像 fast-json-patch / json-ptr 那样的「禁止污染」开关 | ❌ 无控制被绕过 |
| **攻击者能否独立触发** | 不能。必须是**应用**把不可信输入当作 path 传给 `_.get` | ❌ 需要应用层误用 |
| **真实可达性** | 8 个真实应用 / 6457 文件 / 588 调用点 → HTTP 级成立 **0 处**（11-02 实测） | ❌ 无可利用面证据 |
| **维护者视角** | 改 `_.get` 语义会破坏大量合法用法（深路径访问就是这个 API 的全部意义） | ❌ 不可能按漏洞修 |
| **历史一致性** | lodash 有 10 条 advisory，全部集中在**写侧污染**（merge/set/zipObjectDeep/template） | ⚠️ 生态共识：读侧不算 |

**关键区别**：fast-json-patch 有 `banPrototypeModifications` 开关且默认开——**有承诺，绕过才叫漏洞**；
json-ptr 的 `set` 明确拒绝 `__proto__`——**有意图，读侧漏了才叫缺陷**；
lodash 从头到尾没有任何「禁止原型链读取」的设计意图——**没有承诺，就没有违背**。

## 三、那 11-02 的报告白做了吗？没有，但要换定位

仍然成立的、有价值的三条：

1. **分发形态断层是真实的**：18 个兄弟包里 12 个停在 2016-08-13；只有被 advisory 点名的
   （`lodash.merge` / `lodash.defaultsdeep`，CVE-2019-10744）才被捞出来修。
   → 这是**供应链治理**问题：advisory 体系只对「包名被点名」作出反应。
2. **22.3M 周下载的包 0 条 advisory**，这个数字本身值得写进研究笔记——它说明「未被点名」≠「已评估」。
3. **读侧无结构检查**是事实，可作为加固建议（给应用方），而不是 CVE。

正确的出口（三选一，都不走 PVR）：

| 选项 | 做法 | 风险 |
|---|---|---|
| A（推荐） | 写成研究笔记/博客：供应链 advisory 覆盖率的测量研究 | 无 |
| B | 给 lodash 开 **discussion / docs issue**，建议在文档里明确「path 必须可信」 | 低，但大概率 won't fix |
| C | 提交到 GitHub Security Advisory | ❌ **会被拒**，且消耗你在维护者那里的信用 |

## 四、写给自己的一条规则

> **「下载量大 + 无 advisory + 能读到危险对象」≠ 漏洞。**
> 判据只有一个：**这个库是否承诺过阻止这件事**。
> 有承诺（开关/守卫/文档）→ 绕过 = 漏洞；没承诺 → 是 API 语义，最多算加固建议。

这条规则今天同时救了两条线：它让 lodash 免于被拒，也让 json-ptr / fast-json-patch 的提交站得住。
